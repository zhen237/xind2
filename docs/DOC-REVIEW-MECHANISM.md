## 一、复查周期设定

### 1.1 复查频率

| 文档类型 | 复查周期 | 触发条件 |
|----------|----------|----------|
| **核心文档** | 每月一次 | 每月1日自动触发 |
| **技术文档** | 每季度一次 | 每季度第一个月1日触发 |
| **API文档** | 每次接口变更后 | 接口修改提交后触发 |
| **数据库设计文档** | 每次表结构变更后 | SQL脚本提交后触发 |
| **部署文档** | 每半年一次 | 每年1月和7月触发 |
| **全部文档** | 每半年一次 | 年度审计（每年1月和7月） |

### 1.2 复查时间安排

| 周期 | 时间 | 负责人 |
|------|------|--------|
| 月度复查 | 每月第一个工作日 | 文档管理员 |
| 季度复查 | 每季度第一个月第一个工作日 | 技术负责人 |
| 半年复查 | 每年1月和7月第一个工作日 | 项目负责人 |

## 三、复查内容清单

### 3.1 通用检查项

| 检查项 | 检查内容 | 判定标准 |
|--------|----------|----------|
| **版本信息** | 文档开头是否标注版本号和更新日期 | 必须包含版本和日期 |
| **变更记录** | 是否包含变更记录章节 | 必须包含变更记录表 |
| **链接有效性** | 文档内链接是否有效 | 所有链接必须可访问 |
| **格式规范** | 是否符合文档模板规范 | 标题层级、表格格式、代码块 |
| **术语一致性** | 专业术语使用是否统一 | 同一术语全文一致 |
| **内容准确性** | 信息是否与实际代码一致 | 无错误信息 |
| **语言易懂性** | 是否使用通俗易懂的语言 | 避免过度专业术语 |

### 3.2 核心文档专项检查

#### PROJECT-OVERVIEW.md
| 检查项 | 检查内容 |
|--------|----------|
| 项目目标是否清晰 | 描述是否准确反映项目核心目标 |
| 模块列表是否完整 | 是否包含所有实际存在的模块 |
| 技术栈版本是否准确 | 是否与pom.xml/package.json一致 |
| 业务流程是否清晰 | 流程描述是否易于理解 |

#### README.md

| 登录信息是否有效 | 默认账号密码是否可用 |

#### API接口文档.md

|--------|----------|

#### 数据库设计.md

|--------|----------|
| 表结构是否完整 | 是否包含所有实际表 |
| 字段定义是否准确 | 是否与实体类一致 |
| 主键外键是否正确 | 关联关系是否准确 |

#### 开发规范.md
| 检查项 | 检查内容 |
|--------|----------|
| 命名规范是否统一 | 是否覆盖所有语言 |

| Git规范是否执行 | 是否符合团队约定 |

## 四、复查执行流程

### 4.1 复查步骤

```
开始 → 通知责任人 → 执行检查 → 记录问题 → 评估严重程度 → 分配修复任务 → 执行修复 → 验证修复 → 更新记录 → 结束
```

### 4.2 详细流程说明

1. **通知阶段**（提前3天）
   - 文档管理员发送复查通知邮件/群消息
   - 通知内容包含：复查时间、复查范围、责任人

2. **检查阶段**（复查当天）
   - 复查人按照检查清单逐项检查
   - 记录发现的问题及严重程度

3. **评估阶段**（复查当天）
   - 评估问题严重程度（高/中/低）
   - 确定修复优先级

4. **修复阶段**（发现问题后）
   - P0问题：24小时内修复
   - P1问题：3天内修复
   - P2问题：1周内修复

5. **验证阶段**（修复完成后）
   - 复查人验证修复结果
   - 确认问题已解决

6. **记录阶段**（验证通过后）
   - 更新复查记录文档
   - 更新问题所属文档的变更记录

## 六、异常处理流程

### 6.1 问题严重程度定义

| 等级 | 标识 | 定义 | 处理时限 |
|------|------|------|----------|
| **P0** | 🔴 紧急 | 文档信息错误导致系统无法正常运行或安全风险 | 24小时 |
| **P1** | 🟠 重要 | 文档信息不准确影响开发效率或用户体验 | 3天 |
| **P2** | 🟡 一般 | 格式问题、术语不统一等不影响功能的问题 | 1周 |

### 6.2 异常处理流程

```
发现问题 → 评估严重程度 → 通知责任人 → 制定修复方案 → 执行修复 → 验证修复 → 关闭问题
     ↓                              ↓
 超时升级                     无法修复
     ↓                              ↓
 上报技术负责人              上报项目负责人
     ↓                              ↓
 协调资源解决              评估是否接受现状
```

### 6.3 超时处理

| 超时情况 | 处理措施 |
|----------|----------|
| P0超时（超过24小时） | 立即上报技术负责人，协调紧急修复 |
| P1超时（超过3天） | 发送二次提醒，上报技术负责人 |
| P2超时（超过1周） | 发送三次提醒，纳入季度复查重点 |

### 6.4 无法修复处理

| 情况 | 处理措施 |
|------|----------|
| 技术限制无法修复 | 记录原因，上报项目负责人决策 |
| 资源不足无法修复 | 纳入下季度计划，申请资源 |
| 优先级低延后修复 | 标记为P3，在后续版本修复 |

## 七、复查工具与辅助手段

### 7.1 检查工具

| 工具 | 用途 | 使用方式 |
|------|------|----------|
| **链接检查器** | 检查文档内链接是否有效 | 手动检查或使用在线工具 |
| **代码对比** | 对比文档与代码一致性 | 阅读代码确认 |
| **格式验证** | 验证Markdown格式是否规范 | 使用Markdown编辑器验证 |
| **术语搜索** | 搜索术语使用一致性 | 使用IDE搜索功能 |

### 7.2 自动化检查

| 检查项 | 自动化方式 | 频率 |
|--------|------------|------|
| **链接有效性** | CI流程中运行链接检查脚本 | 每次提交 |
| **格式规范** | 使用markdownlint检查 | 每次提交 |
| **版本信息** | 检查文档是否包含版本标记 | 每次提交 |

### 7.3 AI工具使用规范

#### 7.3.1 AI工具检查流程

```
1. 读取项目上下文 → 2. 搜索常见错误模式 → 3. 逐一验证问题 → 4. 制定修复方案 → 5. 执行修复 → 6. 验证修复
```

#### 7.3.2 AI工具前置准备

使用AI工具进行代码检查前，必须：

1. **读取项目概述文档**: [PROJECT-OVERVIEW.md](PROJECT-OVERVIEW.md)
2. **读取AI工具辅助文档**: [AI-TOOL-CONTEXT.md](AI-TOOL-CONTEXT.md)
3. **查看目录结构**: 了解项目组织方式
4. **读取开发规范**: [开发规范.md](开发规范.md)

#### 7.3.3 AI工具检查清单

| 检查项 | 搜索关键词 | 风险等级 |
|--------|------------|----------|
| **硬编码密码** | `password:.*[^$]` | 🔴 高 |
| **硬编码密钥** | `secret:.*[^$]` | 🔴 高 |
| **权限绕过** | `anyRequest().permitAll()` | 🔴 高 |
| **跨域风险** | `targetOrigin.*\*` | 🔴 高 |
| **内存泄漏** | `new Cesium\.Viewer` 无destroy | 🟡 中 |
| **内存泄漏** | `echarts.init` 无dispose | 🟡 中 |
| **调试日志** | `console\.log` | 🟡 低 |
| **SQL注入** | `String.format` + SQL | 🔴 高 |

#### 7.3.4 AI工具修复验证标准

修复完成后必须验证：

1. **代码编译通过**（后端）
2. **构建成功**（前端）
3. **单元测试通过**（如有）
4. **功能验证**（手动或自动化）
5. **无新问题引入**（回归检查）

#### 7.3.5 AI工具使用注意事项

| 事项 | 说明 |
|------|------|
| **上下文先行** | 必须先读取项目文档再进行检查 |
| **逐一验证** | AI发现的问题必须手动验证确认 |
| **避免臆断** | 没有代码证据的问题不应随意修改 |
| **记录完整** | 所有修复必须在变更记录中说明 |
| **版本同步** | 修改后必须更新文档版本号和日期 |
