## S1 · 子赛题1：面向专业GIS平台的通信工程智能辅助设计

**对应角色：老李（通信设计员，画图哥）**

### 老李的痛
打开 CAD，对着空白图手动画基站、管线、机房，画一张半天。画完还得把图**人工翻译成施工单**——哪根缆接哪、多少米，全靠手抄。CAD 没有"自动拓扑""冲突预警"，他也不会用。

### 文件想帮他什么
用 QGIS 这种专业平台，但把门槛降下来：**参数一填 / 区域一框，系统自动出设计图**。核心指标（文件第6页）：辅助设计效率提升 ≥30%，或减少 50% 以上手动绘图操作。

### 我们的设计逻辑（通俗）

S1 不是"画一张图"，而是"**把设计变成一套可重复的规则 + 一个会听话的助手**"。四层：

```
① 低代码交互层（人怎么下指令）
   框选区域 + 填参数（基站密度/管线类型/机房容量）
   → 替代 CAD 里一笔笔画边界

② 拓扑生成层（图怎么自动出来）
   六边形网格撒点定站址 → 最短路径连管线 → 覆盖半径反推机房
   → 这就是"自动化拓扑设计"

③ 真实数据层（设计建立在真实现网上）
   加载摩洛哥 FTTH 现网 Shape（8层）→ 作为设计底图
   → 设计不是画在空白纸，而是叠在真实网络上

④ AI 助手层（真智能在哪）★ 见 m03-llm-service
   人说人话 → 系统翻译成设计参数 → 系统把方案写成评审报告
```

### 技术怎么算（准确版）

| 部件 | 模块 | 内部逻辑 |
|------|------|----------|
| 交互面板 | `qgis-plugin/ui/design_dock.py` | **9 步集成向导**：加载FTTH真实数据→覆盖缺口识别→框选→参数→生成→场景构建(叠加FTTH)→自检/联动→出图（详见 `qgis-plugin/docs/usage-guide.md`） |
| 站址/管线生成 | `qgis-plugin/design_engine/hex_grid.py` | 六边形网格按间距撒点（宏站/微站/室分三套模板）；站间按规则连管线（直埋棕/管道蓝/架空绿） |
| 覆盖计算 | `qgis-plugin/design_engine/`（传播模型） | Okumura-Hata 经验模型算覆盖半径 → 生成覆盖多边形/热力图 |
| 后端生成 | `packages/m03-bim-gis/backend` DesignController/DesignService | 双路径：优先调拓扑引擎，挂了本地回退（只产 sites 不产 deviceLayout）；幂等守卫防重复 |
| 拓扑引擎 | `packages/m03-topology-engine` (FastAPI :9001) | `/generate` 返回 sites(站点) + devices(铁塔/天线/RRU/BBU/电源/传输) + coverage_polygons(覆盖多边形) |
| **真 AI** | `packages/m03-llm-service` (FastAPI :9002) | **①** `/parse-design-params`：自然语言→结构化 DesignParams（带通信工程专业提示词+坐标推断+few-shot）<br>**②** `/generate-report`：设计方案 JSON→专业 Markdown 评审报告（RSRP/SINR/PCI/ISD 全量化） |

### 当前进度：✅ 完整实现
QGIS 插件 + M03 后端 + 拓扑引擎 + LLM 服务四件套全通。38/45 条标准自检、真实数据加载、联动高亮、摩洛哥底图均已落地。**这是五个子赛题里最成熟的一个，也是你答辩的主战场。**

## S2 · 子赛题2：多源异构工程数据融合

**对应角色：小张（数据/档案管理员）**

### 小张的痛
公司十年攒了几千张 CAD 老图纸，全是宝贝。但新平台用 GIS（QGIS），CAD 和 GIS **格式不通**，老图纸打不开、用不上，历史资产白费。

### 文件想帮他什么
把老 CAD 图纸**无损转成 GIS 能用的数据**——图形、属性、拓扑关系全保留。让"历史资产"重新变成可计算的生产资料。

### 我们的设计逻辑（通俗）

S2 干的事本质是**"翻译"**：把一种坐标系/格式里的东西，原样搬到另一种里，且不能丢信息。

```
CAD (.dwg/.dxf)  ──解析──▶  几何(线/面/点) + 属性(图层/标注)
                              │
                              ├─ 坐标变换：CAD 的局部坐标 → 真实经纬度 (EPSG:3857→4326)
                              ├─ 图层映射：CAD 图层名 → GIS 图层/字段
                              └─ 拓扑重建：线段闭合关系 → GIS 拓扑
                              │
                              ▼
                        GIS 可用数据 (Shape / GeoJSON / PostGIS)
```

### 技术怎么算（规划）
- `packages/s2-cad-fusion` (Spring Boot :8082)：规划做 DWG/DXF 解析入口，对外提供"上传 CAD → 返回 GIS 数据"的接口。
- 现成范例：`qgis-plugin/ftth/` 加载的**摩洛哥 FTTH 真实 Shape 数据**，就是"已经融好、能直接进 GIS 的真实资产"的样板——它证明了我们平台能消费异构数据源。

### 当前进度：🟡 规划中（骨架）
`s2-cad-fusion` 目前只有 Spring Boot 启动骨架，无业务代码。但 **FTTH 真实数据加载链路已跑通**，可作为 S2 能力的"演示切片"——答辩时可以说"这是多源数据融合的一个落地实例，CAD→GIS 的通用解析器在扩展中"。

## S3 · 子赛题3：基于行业标准的设计智能审查

**对应角色：王工（设计审查员）**

### 王工的痛
几百张设计图堆过来，靠一双肉眼 + 多年经验审。电力线和通信线交越距离够不够？两条管线会不会打架？全靠目测，根本看不全，出事就是安全事故。

### 文件想帮他什么
把国标规范（电力交越安全距离、资源冲突规则）**变成电脑能算的逻辑**，系统自动全量审查，风险提前预警。

### 我们的设计逻辑（通俗）

S3 = **把王工脑子里的经验，写成"if-then"规则**。

```
设计成果(图/数据)
   │
   ▼  逐条跑规则
规则库（每条 = 一条国标/企标）
   ├─ R01 电力线与通信线交越距离 ≥ X 米？
   ├─ R02 两条管线水平间距 ≥ Y 米？
   ├─ R03 基站距敏感建筑 ≥ Z 米？
   └─ ……（共 38/45 条）
   │
   ▼
违规清单 + 红框高亮 + 整改建议
```

### 技术怎么算（部分实现）
- **前端已实现**：`qgis-plugin/ftth/validate.py` 写了 **38 条（实际扩展到 45 条）自检规则**，覆盖字段完整性、几何合法性、图层间逻辑一致性；`qgis_style.py` 用红框 RubberBand 高亮异常要素（已修好 QGIS 3.44 的 API 坑）。
- **后端规划中**：`packages/s3-review-engine` (Spring Boot :8089) + `rules/` 目录（目前空，规划放 Python 规则引擎）。目标是把插件里的规则引擎化、服务化，支持规则动态配置 + 批量审查报告。

### 当前进度：🟡 部分实现
**规则逻辑已在 QGIS 插件里跑通**（这是最值钱的部分，因为规则就是王工经验数字化），但**后端服务化/Web 化还没做**。答辩策略：演示插件里 38/45 条规则的实际审查效果，同时说明"规则引擎将下沉为独立微服务以支持大批量自动审查"。

## S4 · 子赛题4：设计成果向施工指令的自动转化

**对应角色：陈姐（物料/BOM 编制员）**

### 陈姐的痛
设计一定稿，她得人工算物料清单——光缆多少米、接头多少个、光交箱几台。算错一处，现场就缺料返工。一份 BOM 编一两天。

### 文件想帮他什么
设计定稿**一键生成 BOM、工艺要求、纤芯分配表**。打通"设计→施工"的断点。

### 我们的设计逻辑（通俗）

S4 = **从"设计图"自动推导出"采购单 + 施工单"**。

```
设计成果（站点清单 + 管线长度 + 机房容量）
   │
   ├─ 物料清单(BOM)：光缆长度×单价 → 光缆总米数；接头数；光交箱台数；ODF 端口数
   ├─ 工艺要求：直埋/管道/架空各自的施工工艺说明
   └─ 纤芯分配表：哪条缆用几芯、分给哪些用户
   │
   ▼
施工指令包（可直接下发给刘队）
```

### 技术怎么算（规划）
- `packages/s4-bom-transform` (Spring Boot :8090)：规划做"设计数据 → BOM 结构化输出"的转换引擎（可能含 Python 计算脚本）。
- 输入来源：S1 的设计成果（站点/管线/机房数据）。这是 S1→S4 的自然衔接点。

### 当前进度：🟡 规划中（骨架）
`s4-bom-transform` 只有启动骨架，无业务代码。逻辑清晰（纯几何长度统计 + 物料映射），是五个子赛题里**实现成本最低、最容易补**的一个。建议作为 S1 完成后的下一个发力点。

## S5 · 子赛题5：施工过程智能监管

**对应角色：刘队（施工队长 / 监理）**

### 刘队的痛
带人在现场挖沟埋管线。进度靠打电话汇报；地下埋了什么，完工后看不见、验不准，只能事后抽检。等运维来查，发现和图纸对不上——"数据黑箱"。

### 文件想帮他什么
用视频 / 物联网 / 传感器，让施工和数字化模型**实时对齐**：进度自动跟踪、违章自动识别；隐蔽工程影像**自动分析验真**，形成不可篡改的竣工档案。

### 我们的设计逻辑（通俗）

S5 = **让现场"看得见、验得真"**，把物理世界实时映射到数字世界。

```
现场（人/机/料/法/环）
   │
   ├─ 视频流 → CV 检测（戴安全帽？违规作业？）      [m07-cv-engine]
   ├─ 物联网传感器 → 设备状态/进度上报               [m05-twin-ops]
   └─ 隐蔽工程影像 → AI 验真（埋深/材质对不对）
   │
   ▼  映射到数字孪生
数字孪生体（和 S1 设计图对齐）
   ├─ 进度自动更新
   ├─ 告警自动生成 → 写进交付系统(M04)工单
   └─ 竣工档案不可篡改
```

### 技术怎么算（部分实现）
- **`packages/m05-twin-ops` (:8085) — 较完整**：有 `MqttSubscriber`（订阅物联网消息）、`AlertController`/`DeviceController`（告警+设备状态）、`Alert`/`Device` 实体与 Mapper。已实现"设备状态→告警→落库"的闭环。
- **`packages/m07-cv-engine` (:8088) — 起步**：规划 YOLO 视觉检测（安全帽/违章识别），目前文件较少，需补模型与推理逻辑。
- **`packages/s5-construction-monitor` (:8091) — 骨架**：施工监管主服务，待写业务逻辑。
- 跨模块闭环已存在：m05 的告警会自动写进 `m04-delivery` 的工单系统（"运维告警→自动建交付工单"）。

### 当前进度：🟡 部分实现
m05 数字孪生/告警较完整，m07 CV 检测与 s5 监管服务是骨架。S5 是工程量最大、依赖最多（视频/物联网硬件）的子题，建议作为"远景演示"而非主答辩点。
