# 五人分工方案 — 按官方子赛题重组

**版本**: v1.0
**日期**: 2026-07-13
**方案**: 共享归口 + 独立新建（现有模块不拆分不移动，新功能代码放各赛题独立目录）

---

## 一、总体原则

1. **共享基础设施独立归口** — m01-auth / m06-portal / shared / screen 不归属任何赛题，谁用谁调用（REST API）
2. **现有模块不拆分** — 保持 import / CI/CD / Maven 依赖不变，避免破坏性重构
3. **新功能代码放独立目录** — 各赛题新建 `sN-xxx/` 目录，内部自成体系
4. **M04 按赛题"认领"** — M04 中已有代码按赛题归属，各负责人可扩展/重构属于自己赛题的部分，新功能在新目录开发
5. **跨赛题交互走 REST API** — 禁止跨赛题直接 import Java/Python 代码

## 五、模块间交互方式

### 5.1 后端交互

```
┌─────────────────────────────────────────────────────┐
│                    共享基础设施                       │
│  m01-auth(8080)  m06-portal(5173)  shared  screen   │
└──────────┬──────────────────┬───────────────────────┘
           │ JWT 鉴权          │ iframe 聚合
           ▼                  ▼
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ S1(8083) │  │ S2(8082) │  │ S3(8089) │  │ S4(8090) │  │ S5(8085  │
│          │←─│          │  │          │  │          │  │ 8088     │
│ 设计数据  │  │ CAD融合   │  │ 审查引擎  │  │ BOM转化   │  │ 8091)    │
│          │  │          │  │          │  │          │  │          │
└──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘
      │                                          ▲           ▲
      │  1. S1设计结果 → S3审查                   │           │
      │  2. S1设计结果 → S4生成BOM               │           │
      │  3. S4施工指令 → S5施工监管               │           │
      │  4. S2融合数据 → S1设计参考               │           │
      └──────────────────────────────────────────┘           │
                                                               │
```

**核心数据流：**
1. **S2 → S1**: CAD 融合后的统一数据模型提供给 S1 设计参考
2. **S1 → S3**: 设计结果提交给 S3 进行标准审查
3. **S1 → S4**: 设计成果发送给 S4 生成 BOM 和施工指令
4. **S4 → S5**: 施工指令传递给 S5 进行施工过程监管
5. **S5 → S3**: 施工检测结果反馈给 S3 进行验收审查

### 5.2 前端聚合

```
m06-portal (5173)
├── 登录页 → m01-auth
├── S1 设计模块 → iframe → m03-bim-gis (5174)
├── S2 数据融合 → iframe → s2-cad-fusion/frontend
├── S3 智能审查 → iframe → s3-review-engine/frontend
├── S4 施工转化 → iframe → s4-bom-transform/frontend
├── S5 施工监管 → iframe → s5-construction-monitor/frontend
└── 数据大屏 → screen (8086)
```

### 5.3 通信协议

| 场景 | 协议 | 说明 |
|------|------|------|
| 赛题间数据传递 | REST API (HTTP) | 同步调用，JWT 鉴权 |
| 实时数据推送 | WebSocket | S5 施工监管实时告警 |
| 文件传输 | MinIO | 设计文件、BOM 文件、影像文件 |
| 消息队列 | EMQX (MQTT) | S5 设备物联网数据 |

# 请求头（所有赛题 API 必须携带）
Authorization: Bearer <jwt_token>

POST /auth/login          # 登录，返回 JWT
GET  /auth/user/info      # 获取当前用户信息

### 7.2 m06-portal 前端门户

### 7.3 shared 共享代码

```xml
<!-- 各赛题 backend 的 pom.xml 引入 shared -->
<dependency>
    <groupId>com.comm</groupId>
    <artifactId>shared</artifactId>
    <version>${project.version}</version>
</dependency>
```

共享内容包括：
- `Result<T>` — 统一响应包装
- `PageResult<T>` — 分页响应
- `BusinessException` — 业务异常
- `SecurityStarter` — JWT 安全自动配置
- `CacheStarter` — Redis 缓存自动配置

### 🟡 P1 — 第一周内解决

#### 6. pom.xml 父 POM 未包含新模块

#### 7. docker-compose.yml 缺少新模块服务定义

**现状**: docker-compose 只定义了基础设施（MySQL/Redis/MinIO/InfluxDB/EMQX），无应用服务。
**对策**: 各赛题提供 Dockerfile 后，在 docker-compose.yml 中添加服务定义。或在 docs 中提供 `docker-compose.override.yml` 模板。

#### 8. CI/CD 只覆盖 m03-bim-gis 前端

**现状**: `.github/workflows/deploy.yml` 只对 m03-bim-gis/frontend 做 ESLint + Prettier + build。
**遗漏**: 
- 无后端 Java 编译/测试
- 无 QGIS 插件测试
- 无新模块前端 lint
**对策**: deploy.yml 添加 matrix job，覆盖各赛题模块。

#### 9. 数据库表前缀归属未明确

**现状**: M04 所有表用 `m04_` 前缀（m04_acceptance_task, m04_safety_check, m04_delivery_package 等）。
**问题**: 代码迁移到 s3/s4/s5 后，表名是否改前缀？
**建议**: **迁移期间保持 m04_ 前缀不变**，避免 Flyway 迁移脚本断裂。新模块新增的表用各自前缀（`s3_`, `s4_`, `s5_`）。完全迁移后再考虑重命名。

#### 10. Flyway 迁移脚本归属

**现状**: M04 使用 Flyway，迁移表为 `flyway_schema_history_m04`，脚本在 `classpath:db/migration`。
**问题**: 代码迁移后，Entity 和 Mapper 搬走了但 Flyway 脚本还在 M04 里。
**建议**: 迁移期间 Flyway 脚本留在 M04 不动。新模块用各自的 Flyway 表（`flyway_schema_history_s3` 等），只管理新增表。

#### 11. 共享数据库 vs 独立数据库

**未明确**: 新模块是否使用独立数据库？
**建议**: **统一使用同一个 MySQL 数据库** (`comm_platform`)，通过表前缀区分。理由：
- 比赛演示环境资源有限
- 跨模块查询（如 screen 大屏聚合）不需要跨库 JOIN
- M04 迁移期间表不改名，同库最简单
