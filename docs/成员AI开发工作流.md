# 成员 AI 开发工作流

> 配套文档：`团队AI启动指令.md`（找到自己赛题那段，全文复制）
> 本文讲"怎么用 AI 把活干完"，不重复讲"能改哪些目录"。

---

## 总体原则

AI 不是替你写代码，是**按规范帮你写代码**。你负责定方向、做决策、验收结果；AI 负责查文档、写实现、跑测试。

**最佳实践顺序**：先让它读懂项目 → 再让它做小任务 → 你验证 → 再下一个。

**统一技术约定**（Python 版本、UI 风格、不用 Docker 等）见 `团队AI启动指令.md` 的「互不干扰规则」表，全员按同一套执行。

---

## 第一步：环境跑通（不用 AI）

1. 装好 Git、JDK 17
2. `git clone` 项目 → 切到自己的 `feat/sX-xxx` 分支
3. 本地启动依赖（MySQL / Redis），或仅用自己模块自带的依赖（不使用 Docker）
4. 启动自己的模块，确认门户能打开、自己模块能跑

环境没跑通之前，不要急着让 AI 写功能。

---

## 第二步：把启动指令喂给 AI

1. 打开 AI 工具（WorkBuddy / Claude / Cursor / Copilot）
2. 从 `团队AI启动指令.md` 复制**自己赛题**那段，作为第一条消息发出
3. 紧接着发一句：**"请先按顺序读上面列出的必读文档，读完后告诉我你理解了哪些模块边界和接口契约。"**
4. 等 AI 回复确认它理解了边界，再开始派活

> 这一步最关键。AI 没读文档就动手，很容易写出不符合规范的代码、或碰了别人的目录。

---

## 第三步：分小任务派活（核心）

不要一次说"把整个 S2 做完"。拆成小任务，逐个验收：

**好的派活方式：**
- "先实现 CAD 文件上传接口 `POST /api/v1/s2/cad/parse`，参考 `packages/s2-cad-fusion/README.md` 里的 API 约定，写好后跑一下编译"
- "上传接口好了，现在加坐标系转换工具类，支持 WGS84 ↔ CGCS2000，写单元测试覆盖边界值"
- "转换工具测试通过后，把结果转成 GeoJSON 输出"

**不好的派活方式：**
- "把 S2 全部做完"（太宽泛，AI 会自由发挥，容易出界）

每完成一个小任务，**你本地跑一下验证**（编译 / 启动 / 接口调用），通过了再派下一个。

---

## 第四步：验证与提交

1. AI 写完后，你亲自跑一遍（启动服务、调接口、看页面）
2. 确认没改到别人的目录（`git status` 看改动文件）
3. 自测没问题再 `git add` + `git commit`
4. **禁止 `git push --force`**
5. 需要合并到 main 时开 PR，系统会自动拉负责人 review

---

## 试运行数据让 AI 生成

能用脚本造的样例数据（GeoJSON 图层、设备记录、模拟告警等），不要手工填，直接让 AI 写生成脚本：

- "写一个 Python 脚本，生成 50 条运城学院样例基站数据，导出为 GeoJSON，字段参考 S1 的 Region 模型"
- "生成一批模拟施工告警记录，存到本地 MySQL 的 alert 表，供我本地试运行"

生成脚本放在自己模块目录下，跑出来的数据只用于本地试运行，不进 Git 主干。

---

## 三条红线（违反会打乱团队）

| 红线 | 说明 |
|------|------|
| 不碰别人目录 | 只改自己赛题的模块，共享模块(m01/m06/shared/screen)改了要走 PR |
| 跨赛题只走 API | 不能 `import` 别人的 Java/Python 代码，数据通过 REST API 传 |
| 不伪造测试结果 | AI 说"测试通过"你要自己跑一遍确认，别直接信 |

---

## 碰到问题怎么办

- **AI 写的跑不起来**：把报错日志贴给它，让它修，别自己硬调
- **AI 想改共享模块**：先在高/王确认后再动，或开 PR 等 review
- **不确定接口怎么对接**：看 `docs/技术架构与开发规范.md` §5.5 跨赛题接口契约，或直接问对接方
- **环境起不来**：看 `docs/本地部署指南.md` 的排查清单，或群里问
