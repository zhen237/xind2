## 一、文档完整性评估

### 1.1 现状

| 文档类型 | 状态 | 问题 |
|----------|------|------|
| API接口文档 | ⚠️ 严重不足 | 技术架构与开发规范.md §5 仅列了 M03 的 6 个接口路径，无请求/响应字段定义。M01/M04/M05/M07 的 API 完全未文档化。S1→S3、S1→S4、S4→S5 的跨赛题接口只提了数据流方向，没有接口契约。 |
| 数据库设计 | ⚠️ 不足 | §3 只有表名清单和少量索引示例，缺少完整建表 DDL、字段定义、约束、外键关系。实际 DDL 散落在各模块的 Flyway 脚本和 scripts/init-mysql.sql 中。 |
| 模块说明 | ❌ 缺失 | **没有任何模块级 README**。packages/ 下 8 个模块无一个有 README.md。新成员不知道每个模块的启动命令、配置说明、依赖关系。 |
| 配置指南 | ⚠️ 不一致 | 有 .env.example 但配置项分散在根目录和各模块。application.yml 的密码默认值不统一（M01: `root123`，M03: `CHANGE_ME_IN_DEVELOPMENT`，M04: 无默认值强制要求环境变量）。 |
| 数据结构定义 | ⚠️ 分散 | Java Entity 是唯一的数据结构定义来源，但没有独立的 DTO/Schema 文档。前端开发者必须读 Java 源码才能知道接口字段。 |

### 1.2 核心问题

**问题1: 无 OpenAPI/Swagger 自动文档**

项目没有集成 `springdoc-openapi`，无法自动生成 API 文档。在 5 人独立开发的场景下，这意味着：
- S3 开发者不知道 S1 的设计数据接口长什么样
- S4 开发者不知道 S1 的设计成果字段有哪些
- 前端开发者必须翻 Java Controller 源码才能对接

**问题2: 跨赛题接口契约未定义**

五人分工方案 §5.1 定义了数据流方向（S2→S1, S1→S3, S1→S4, S4→S5, S5→S3），但没有任何一处定义这些接口的具体契约：
- S1 向 S3 提交审查时，请求体包含哪些字段？
- S4 向 S5 传递施工指令时，数据格式是什么？
- S5 向 S3 反馈施工检测结果时，字段结构是什么？

**问题3: 部署指南过时**

`本地部署指南.md` 存在多处问题：
- 第20行引用已删除的 `环境依赖版本.md`
- 环境变量示例写 `jdk-21`，项目现已统一采用 JDK 21（与部署指南一致）
- 缺少 M05/M07/Screen 的启动步骤
- 缺少 Docker 基础设施（MySQL/Redis/MinIO/EMQX）的启动说明
- 缺少 Flyway 数据库迁移说明
- 访问地址表未包含 M05(8085)/M07(8088)/Screen(8087)

### 1.3 改进建议

| 优先级 | 建议 | 说明 |
|--------|------|------|
| P0 | 集成 springdoc-openapi | 在 shared 中添加依赖，各模块自动生成 Swagger UI，解决 API 文档自动化 |
| P0 | 定义跨赛题接口契约 | 在技术架构文档中新增 §5.5，定义 S1→S3/S1→S4/S4→S5/S5→S3 的请求/响应 JSON Schema |
| P0 | 修复部署指南 | 更新引用、补充缺失模块启动步骤、补充 Docker 启动、修正 JDK 版本 |
| P1 | 每个模块添加 README.md | 包含：模块职责、启动命令、端口、依赖模块、配置项说明、本地调试方法 |
| P1 | 提取完整 DDL 文档 | 从 Flyway 脚本中提取，形成独立的数据库 Schema 文档，含字段/类型/约束/索引 |

### 2.2 核心问题

- pom.xml 父 POM 未注册新模块
- m06-portal 的渐进迁移机制（VITE_FE_S2~S5）无法验证

**问题3: 空壳模块造成认知负担**

m07-cv-engine（S5 核心组件）只有空目录和 README，m05-twin-ops/frontend 和 screen/frontend 也只有空目录。新成员打开这些目录会困惑：是在开发中？还是废弃了？

## 三、模块间影响隔离评估

### 3.1 现状

| 隔离维度 | 状态 | 风险 |
|----------|------|------|
| 数据库 | ⚠️ 共享单库 | 所有模块共用 `comm_platform` 数据库，仅靠表前缀区分 |
| 配置 | ⚠️ 不一致 | M03 不引用 application-shared.yml，自行内联 Redis 配置；M01/M04 配置风格不同 |
| 代码依赖 | ✅ 走 REST API | 赛题间禁止直接 import，通过 REST 调用 |
| Maven 依赖 | ✅ 独立 | 各模块只依赖 shared-backend，不互相依赖 |
| 端口 | ✅ 无冲突 | 端口分配表清晰，已修复 P0 冲突 |
| 安全配置 | ⚠️ 不一致 | M03 的 permit-paths 过于宽泛（整个 /api/m03/design/** 无需认证） |

### 3.2 核心问题

**问题1: 共享数据库是最大的耦合点**

所有模块写入同一个 MySQL 数据库，通过表前缀（m01_/m03_/m04_/m05_/s2_）区分。这意味着：
- 任何一个模块的 Flyway 迁移失败 → 全部模块启动失败
- 任何一个模块的慢查询 → 影响所有模块性能
- 数据库 schema 变更没有隔离边界

方案文档（§十一.11）确认了"统一使用同一个 MySQL 数据库"的决策，理由是"比赛演示环境资源有限"。这在比赛场景下可接受，但需要明确约束。

**问题2: 配置一致性差**

三个模块的 application.yml 配置风格不一致：

| 配置项 | M01 | M03 | M04 |
|--------|-----|-----|-----|
| 密码默认值 | `root123` | `CHANGE_ME_IN_DEVELOPMENT` | 无默认（强制环境变量） |
| Redis 配置 | 不引入 shared | 自行内联完整配置 | 不引入 shared |
| Actuator | 不配置 | 自行配置且暴露 env/loggers | 不配置 |
| shared.yml 引入 | ❌ 未引入 | ❌ 未引入 | ❌ 未引入 |

**没有任何模块实际引入了 `application-shared.yml`**，尽管 shared/backend 中已经写好了。每个模块都在重复配置 Redis/JWT/Actuator，且配置值不一致。

**问题3: M03 安全配置过于宽泛**

```yaml
security:
  permit-paths:
    - /api/m03/design/**   # 整个设计 API 无需认证
    - /api/m03/model/**    # 整个模型 API 无需认证
    - /api/m03/project/**  # 整个项目 API 无需认证
```

这意味着任何人都可以不带 Token 访问 M03 的所有核心接口。注释说"QGIS 插件调用 API（内网，无需 JWT）"，但生产环境部署后这些接口通过 Nginx 对外暴露。

**问题4: M04 内部赛题耦合**

M04 是单一 Maven 模块，王/庞/李三人各自修改其中的不同 Entity/Service，但：
- 共享同一个 pom.xml → 依赖变更影响所有人
- 共享同一个 application.yml → 配置变更影响所有人
- 共享同一个 Flyway 迁移目录 → DDL 变更影响所有人
- Git 合并冲突高发

### 3.3 改进建议

| 优先级 | 建议 | 说明 |
|--------|------|------|
| P0 | 统一 application.yml 风格 | 所有模块引入 `application-shared.yml`，删除重复的 Redis/JWT/Actuator 配置 |
| P0 | 收紧 M03 安全配置 | 将 permit-paths 限定到真正需要的接口（QGIS 内网调用），其余加 JWT |
| P0 | 统一密码默认值策略 | 全部使用 `${MYSQL_PASSWORD:CHANGE_ME}` 格式，禁止硬编码 `root123` |
| P1 | M04 内部建立代码隔离规则 | 在 ARCHITECTURE.md 中标注赛题边界，CI 检查跨赛题文件修改 |
| P1 | 补充数据库变更管理规范 | 定义 Flyway 脚本命名规则（V{version}__{module}_{description}.sql）、禁止跨模块修改他人表 |
| P2 | 评估读写分离可行性 | screen 大屏查询走只读副本，减少主库压力 |

## 四、公共规范评估

### 4.1 现状

技术架构与开发规范.md §6 定义了基础编码规范，但多个关键领域缺失：

| 规范类型 | 状态 | 详情 |
|----------|------|------|
| 命名规范 | ✅ 有 | Java/Vue/Python 命名规则清晰 |
| Git 提交规范 | ✅ 有 | type(scope):subject 格式，scope 覆盖全部模块 |
| 安全规范 | ✅ 有 | 禁止硬编码/permitAll/postMessage(*)/SQL拼接/System.out |
| **错误码体系** | ❌ 缺失 | 只说"用 BusinessException(code, msg)"，但未定义错误码范围分配（M01用什么段？M03用什么段？S2-S5用什么段？） |
| **日志规范** | ❌ 缺失 | 只说"用 SLF4J"，未定义：日志级别使用标准（什么时候 WARN vs ERROR）、结构化日志格式、敏感信息脱敏规则、日志保留策略 |
| **测试规范** | ❌ 缺失 | 未定义：最低测试覆盖率要求、单元测试 vs 集成测试边界、Mock 策略、测试命名规范 |
| **DTO/VO 规范** | ❌ 缺失 | 未定义：请求/响应 DTO 命名规则（XxxRequest/XxxResponse/XxxDTO？）、DTO 与 Entity 转换规范、字段校验注解使用标准 |
| **API 版本化** | ⚠️ 不完整 | 只说"/api/v1/sN/**"，未定义版本升级策略和向后兼容规则 |
| **异常处理策略** | ⚠️ 不完整 | 只说"用 GlobalExceptionHandler"，未定义：可重试 vs 不可重试异常分类、异常信息国际化、前端如何解析错误响应 |
| **代码审查标准** | ❌ 缺失 | 未定义 PR review checklist、必检项、合并条件 |

### 4.2 核心问题

**问题1: 没有错误码体系**

5 人独立开发，如果没有统一的错误码分配，会出现：
- M01 返回 code=10001，M03 也返回 code=10001 → 前端无法区分来源
- S2-S5 新模块不知道该用什么错误码段
- 前端无法根据 code 做精确的错误处理

建议分配：
```
M01:  1000-1999
M03:  3000-3999
M04:  4000-4999
M05:  5000-5999
S2:   2000-2999
S3:   3000-3999 (与M03协调)
S4:   4000-4999 (与M04协调)
S5:   5000-5999 (与M05协调)
共享:  9000-9999
```

**问题2: 没有日志标准**

M03 的 application.yml 设了 `logging.level.com.comm.m03: DEBUG`，但没有全局日志标准。5 人各自开发会出现：
- 有人用 `log.info()` 打详细调试信息，有人用 `log.debug()`
- 日志格式不统一（有人带 traceId，有人不带）
- 敏感信息（密码、Token）可能被打到日志里

**问题3: 没有测试要求**

当前只有 M01 有测试代码（AuthControllerTest, JwtUtilsTest），M03 有少量集成测试（DesignIntegrationTest）。其他模块零测试。没有定义：
- 新增功能是否必须带单元测试
- PR 是否必须通过测试才能合并
- 测试覆盖率最低要求

### 4.3 改进建议

| 优先级 | 建议 | 说明 |
|--------|------|------|
| P0 | 定义错误码体系 | 在技术架构文档 §6 新增 §6.6 错误码分配表 |
| P0 | 定义日志规范 | §6 新增 §6.7：日志级别标准、结构化格式、敏感信息脱敏 |
| P1 | 定义测试规范 | §6 新增 §6.8：测试分层、命名规范、覆盖率要求（建议行覆盖≥60%） |
| P1 | 定义 DTO 规范 | §6 新增 §6.9：DTO 命名/校验/转换规则 |
| P1 | 定义 PR Review Checklist | 在项目管理规范.md 中新增代码审查清单 |
| P2 | 定义 API 版本化策略 | 明确 v1→v2 的迁移规则和向后兼容期 |

## 五、开发接入流程评估

### 5.1 现状

| 接入环节 | 状态 | 问题 |
|----------|------|------|
| 环境搭建文档 | ⚠️ 过时 | 部署指南引用已删除文件、JDK版本矛盾、缺少Docker/Redis/MinIO/EMQX启动 |
| 一键启动脚本 | ⚠️ 部分 | 有 scripts/start-all.bat 但只覆盖部分模块，无 Docker 基础设施启动 |
| 环境变量管理 | ⚠️ 分散 | 根 .env + m06-portal/.env + 各模块 .env.example，需要手动配置多处 |
| IDE 配置指南 | ❌ 缺失 | 无 IntelliJ IDEA/VS Code 配置指南（推荐插件、代码风格、运行配置） |
| 验证流程 | ❌ 缺失 | 无"环境搭建完毕后如何验证"的检查清单 |
| 故障排查 | ⚠️ 不足 | 部署指南只列了3个常见问题，缺少端口冲突/Flyway失败/Redis连接/CORS等 |
| 新模块脚手架 | ❌ 缺失 | S2-S5 新模块无创建脚本或模板 |

### 5.2 核心问题

**问题1: 新成员无法在1小时内跑起来项目**

一个新成员加入后，要跑起来项目需要：
1. 安装 JDK 21 + Maven + Node 22 + MySQL 8 + Redis 7 + QGIS 3.34（部署指南未提 Redis/QGIS 版本）
2. 配置 JAVA_HOME / MAVEN_HOME / PATH
3. 克隆代码仓库
4. 创建 MySQL 数据库 `comm_platform`（部署指南未提这一步）
5. 执行 init-mysql.sql 初始化（部署指南未提这一步）
6. 配置根 .env 文件（密码、JWT Secret 等）
7. 配置 m06-portal/.env 文件
8. 启动 Redis（部署指南未提）
9. 启动 M01 后端
10. 启动 M03 后端 + 前端
11. 启动 M04 后端 + 前端
12. 启动 M06 门户
13. 访问 http://localhost:5173 验证

这个流程在文档中是断裂的——没有一个地方能引导新成员从头到尾完成。

**问题2: Docker 基础设施未被利用**

docker-compose.yml 定义了 MySQL/Redis/MinIO/EMQX，但部署指南完全没提 `docker-compose up -d`。新成员可能手动安装 MySQL 和 Redis，而不是用 Docker。

**问题3: 无环境验证检查清单**

部署完环境后，新成员无法确认"我的环境是否正确"。应该有一个验证脚本：
```bash
# 验证环境
java -version          # 期望: 21.x.x
mvn -v                 # 期望: 3.9+
node -v                # 期望: 22.x
mysql --version        # 期望: 8.0+
redis-cli ping         # 期望: PONG
curl localhost:8080/api/m01/health  # 期望: {"status":"UP"}
```

**问题4: 新模块创建无指引**

## 七、总结

项目的**架构设计是合理的**——五人分工方案、模块边界、端口分配、迁移策略都经过了深思熟虑。问题出在**执行层面**：

1. **文档与代码不同步**：技术架构文档描述了 Python AI 微服务和 S2-S5 模块，但代码中都不存在
2. **基础设施准备好了但没接上**：application-shared.yml 写好了但没人用，docker-compose.yml 定义了但部署指南没提
3. **安全配置在原型阶段就松了**：M03 全接口免认证，这在比赛演示时可接受，但需要标注为技术债
4. **新成员入口断裂**：没有一个完整的"从零到跑起来"的引导路径

核心建议：**先把 P0 的 7 项做完，5 个人才能真正并行开发**。否则任/王/庞/李打开项目后会发现——没有目录、没有接口契约、没有配置模板——只能等高一个人推进。
