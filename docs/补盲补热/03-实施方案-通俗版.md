## 一、先用一句话说清这个功能

> **给一片区域做一次"手机信号体检"：先算出哪里信号弱，再自动告诉你"这儿该补一个基站"，你点一下采纳，它就把站加上、把线拉到机房、把材料单一并开出来。**

整条链是这样走的：

```
发现哪里信号弱  →  在哪儿补站  →  采纳成正式站  →  拉线到机房  →  出材料清单
   （诊断）         （选址）        （落库/上图）      （布线）      （BOM）
```

和传统做法的区别：

| | 传统做法 | 本功能 |
|---|---|---|
| 找弱区 | 靠经验在地图上圈，或者等用户投诉 | 用路径损耗公式逐格算 RSRP，图上直接看得到 |
| 定选址 | 手工取点，凭感觉 | 每片弱区自动给一个建议站 + 一个"紧迫度"评分 |
| 出料单 | 开 CAD/Excel 手填 | 一键出，且按制式自动带 4G/5G 设备项 |
| 耗时 | 小时级 | 分钟级（目标 3 分钟内走完全流程） |

⚠️ **必须说清的一件事**：官方赛题命题书里**没有**"补盲补热"这四个字（全文检索"补盲/补热/弱覆盖/盲区/站址/选址/站间距/链路预算/覆盖半径"均 0 命中）。命题书唯一提到"覆盖"的地方是"**审查**覆盖率≥80%"，指的是**审查体系的覆盖面**，跟无线信号覆盖是两回事。

所以本功能的定位是 **我方自选亮点功能**，不是赛题硬指标。这决定了方案取舍原则：

- 优先"**能演示、算法讲得清**"，不追求工程完备；
- 允许用示意参数，但**必须标注"待校准"**，不许伪装成实测值；
- 范围从严裁剪，宁可少做，也不能把现有演示路径搞坏。

## 二、现有插件长什么样（我看过代码后的事实）

### 2.1 插件是个什么形态

它是一个 **QGIS 桌面插件**（Python + PyQGIS/Qt），不是网页。所有界面都挂在一个主面板上：

| 目录 | 装什么 | 文件数 |
|---|---|---|
| `ui/` | 界面层。主面板 `design_dock.py`（约 6800 行，一个类扛全部） | 25 |
| `design_engine/` | 算法层。覆盖计算、六边形布站、管线、导出 | 33 |
| `models/` | 数据模型。站点、天线、机房、管线、制式 | 21 |
| `layers/` | 地图图层。站点、管线、覆盖范围 | 12 |
| `ftth/` | 光纤接入（FTTH）那一套，跟蜂窝基站是两套独立模型 | 65 |
| `tools/` | 地图交互工具（点选加站等） | 19 |
| `docs/` `tests/` `resources/` `sql/` `examples/` | 文档、测试、图标资源、SQL、示例 | — |

> 蜂窝基站（本次要做的）和 FTTH（本次不碰）**在插件里是并行的两套东西**，各写各的数据结构，只有"机房"算是个弱关联点。

### 2.2 现在的 7 步流程

主面板是一条**线性的 7 步引导**，用户按顺序点：

| 步 | 名称 | 干什么 | 代码位置 |
|---|---|---|---|
| ① | 环境·底图 | 加载地图底图 | `_build_step1:1215` |
| ② | FTTH现网 | 导入/查看现网光纤资源 | `_build_step2:1276` |
| ③ | 设计区域 | 圈定规划范围 | `_build_step4:1347` |
| ④ | 基站参数 | 设制式、频段、塔高、扇区等 | `_build_step5:1399` |
| ⑤ | 生成布局 | 用六边形网格算法批量生成站点 | `_build_step6:1555` |
| ⑥ | 管线·场景 | 生成管线路由、机房 | `_build_step7:1621` |
| ⑦ | 出图·交付 | 导出 CAD/PDF/xlsx/图册 | `_build_step9:1833` |

（注意每个步骤页的方法名和它的显示序号是对不上的：`_build_step4` 是第③步、`_build_step5` 是第④步、`_build_step9` 是第⑦步 —— 这是历史遗留，改的时候要小心。）

### 2.3 一个关键发现：这个功能以前有过，是被删掉的

代码里 `ui/design_dock.py:783` 留着一行注释：

> 步骤按钮（严格按 S1 操作流程 7 步，从上到下；**已删除「覆盖缺口识别」第③步**、「自检·联动」原第⑦步）

也就是说，**原来的第③步就叫「覆盖缺口识别」**，后来被删了。而且删除之后，`ftth/coverage_gap.py` 这份文件还躺在仓库里：

| 函数 | 干什么 | 现状 |
|---|---|---|
| `analyze_coverage_gap:78` | 分析覆盖缺口 | 写完了，**全仓零调用** |
| `_cluster_gap_sites:166` | 按 400m 网格聚类 + 需求评分 | 同上 |
| `build_suggested_sites_layer:285` | 生成"建议站点"图层 | 同上 |

我全仓 grep 过，**没有任何 UI 代码调用它**（`grep -rn "coverage_gap"` 排除自身后为空）。而 `design_dock.py:258` 还留着一个 `self._suggested_sites_layer` 属性，注释直接写着"已弃用"。

**结论**：本次要做的事，本质是**把被删掉的那一步，用一个更靠谱的算法重新加回来，并且把这条断掉的接线接上**。但要注意，`coverage_gap.py` 是 **FTTH 场景**（判断光纤能不能盖到楼栋），**不能直接照搬**，只能参考它的算法骨架（网格聚类、评分、图层），判定逻辑要整体换成蜂窝 RSRP。

### 2.5 四个必须先知道的"坑"

**坑一：站点数据在插件里有"两套格式"，而且不同步。**

- 一套是标准模型：`models/site.py:9` 的 `@dataclass Site`，字段有 `site_id / name / longitude / latitude / site_type / tower_type / tower_height / mount_type / scenario / status / tech_generation / coverage_radius / capacity / antennas / properties`。
- 另一套是界面实际在用的**裸字典（dict）**，写死在 `ui/design_dock.py:2427-2444`（算法生成路径）和 `2485-2499`（手点路径），里面的键是 `band / frequency / power / gain / num_sectors / tech_generation / capacity / coverage_radius`。
- 两套字段**对不上**，中间靠 `_show_bom_dialog:6525` 和 `_export_report_xlsx:4378` 做转换。

更麻烦的是：**界面里的这两条裸字典路径自己也不一致**。我逐行比对过：

| 键 | 算法生成路径 `:2427-2444` | 手点路径 `:2485-2499` |
|---|---|---|
| `site_id` `name` `longitude` `latitude` `tower_height` `site_type` `num_sectors` `scenario` `band` `frequency` `power` `gain` `is_valid` | ✅ | ✅ |
| `tech_generation` | ✅ | ❌ **缺** |
| `capacity` | ✅ | ❌ **缺** |
| `coverage_radius` | ✅ | ❌ **缺** |

也就是说，**手动点出来的站点，字典里根本没有制式、容量、覆盖半径这三个键**，读取方只能靠默认值兜底。这解释了为什么"手动加的站出料单时设备项可能不对"。

**后果**：新增站点时如果只写了一套、或者漏了键，**材料清单和报表导出就会缺项**，而且**不会报错**，只是少东西 —— 属于最难查的那类问题。本功能采纳建议站时，必须把上面**所有**键都写全（这也是为什么要把字段映射表当成头等大事）。

**坑二："覆盖率"这个词在插件里有三种含义，别混。（v1.6 补充）**

| 出处 | 定义 | 性质 |
|---|---|---|
| `_show_coverage_stats:4203` 的"覆盖率(≥-80dBm)" | RSRP ≥ −80 dBm 的格子占比 | **达标线**（"优质覆盖"） |
| 本功能第⑥步的 **可用覆盖率（v1.6）** | RSRP ≥ 弱覆盖阈值（默认 −100 dBm）的格子占比 | **可用线**，与"弱/盲"同一刻度，严格互补 |
| 本功能的 −100 / −110 dBm | 弱覆盖 / 盲区的**分级线** | 分级 |

⚠️ **v1.6 关键更正**：v1.5 时曾计划让第⑥步的覆盖率也沿用 ≥−80dBm。**实测后作废**——因为第⑥步的 RSRP 口径已收严约 28 dB（见环节 1 的"口径修正"），继续用 −80 会算出 **11.3%**，而第⑦步热力图同区显示 **100%**，同屏差 **8.85 倍**。改用弱覆盖阈值后实测 **86.1%**，且满足 `可用覆盖率 + 弱覆盖占比 + 盲区占比 = 100%`，能自圆其说。

**界面上仍必须把两个口径摆出来**（诊断口径 ≠ 热力图口径），否则答辩时评委会抓到自相矛盾。

**坑三：站点表里的"覆盖半径"列，是个假的。**

站点表共 13 列（`_build_site_table:2047`）：

```
站点ID | 名称 | 站型 | 场景 | 塔高(m) | 频段 | 频率(MHz) | 功率(W) | 方位角 | 覆盖半径(km) | 站间距(km) | 坐标 | 安装方式
```

其中"覆盖半径(km)"这一列的值 = **站间距 × 1.5**，也就是说**全表所有站点显示的都是同一个数**，跟站点本身没关系（`_update_site_table:6465` 附近计算）。

→ 本功能的"建议半径"**另开一列放**，不去动这个旧列，避免牵连现有功能。

**坑四：第④步的「场景」下拉框，选了等于没选。**

这条是我这次逐行对源码才发现的，而且跟本功能直接相关。

第④步「基站参数」里有个「场景」下拉框，能选 **城市 / 郊区 / 农村**。但第⑤步生成布局时，**这个值压根没传给生成函数**：

```python
# ui/design_dock.py:2417-2423  实际调用长这样
engine_sites = generate_sites_from_grid(
    centers, config,
    site_type=...,
    tower_height=...,
    num_sectors=...,
    bbox=bbox,
)                    # ← 少了 scenario=...
```

而函数签名里 `scenario` 的默认值是 `"URBAN"`（`design_engine/hex_grid.py:77`）。后果：

- 批量生成的站，ID 全是 `BTS-URBA-001`、名字全是 `URBAN-001`；
- 站点表「场景」列**永远显示 URBAN**，不管你选的是郊区还是农村；
- 反倒是**手动点选的站**取的是面板值（`:2493`），是对的 —— 所以同一个面板里，算法站和手点站的「场景」不一样。

→ 本功能补站时，`scenario` **取第④步面板的值**（跟手点路径口径一致）。**这个既有 bug 本次不修**（修它要动第⑤步，会扩大回归面），只在文档里记一笔。

## 三、总体方案

### 3.1 一句话方案

> **在现有 7 步流程的第⑤步（生成布局）之后，插入一个新步骤「⑥ 弱覆盖诊断 · 补站」，原⑥管线·场景 → ⑦、原⑦出图·交付 → ⑧（7 步 → 8 步）。**

为什么插在第⑤步**之后**，而不是更靠前：

1. **诊断对象在第⑤步才存在。** 第④步「基站参数」**只设参数**（预设方案、制式、频段、塔高、扇区），一个站点都不产生；站点是第⑤步「生成基站布局」按钮产出的（`_build_step6:1555` → `_generate_layout:5632`）。若插在第④步之后，用户点「覆盖诊断」时站点池还是空的 —— 没站点就没法算 RSRP，栅格全是 `-200` 无覆盖哨兵值，**图上会显示"整片区域都是盲区"**，等于诊断了个寂寞。
2. **叙事反而更真实**：变成"设参数 → 生成初版布局 → **发现哪儿还漏** → 补站 → 拉线 → 出图"。这才是真实工程设计流程 —— 先排一版，再查漏补缺。原来那个位置讲不通，因为"还没设计就查漏"。
3. **布线几乎零成本**：补的站先于第⑦步进站点池，用户到第⑦步点「生成管线」时**自动就被拉线了**（依据见下文环节 6）。

> ⚠️ **修正记录（2026-09-19）**：PRD 与架构设计文档 v1.0 都写成"插在④⑤之间"，**那是错的**。已全部修正为"插在⑤之后"。修正后还附带一个好处：第⑤步的硬索引恰好不用动，需要改索引的原有步骤从 3 个减到 **2 个**（⑦管线·场景、⑧出图·交付）。

### 环节 1｜算信号（RSRP 栅格）

**目标**
在设计区域里铺一张方格网，算出每个格子上"手机能收到多强的信号"。这是整条链的地基 —— 没有它，后面"哪里弱"就无从谈起。

**输入**

| 输入项 | 从哪来 | 说明 |
|---|---|---|
| 站点集合 | 现有站点表（`generated_sites`） | 需要：经度、纬度、塔高 |
| 设计区域范围 | 第③步"设计区域"圈定的范围 | 决定网铺多大 |
| 频段参数 | 第④步面板选的频段 | 频率、功率、天线增益 |
| 采样分辨率 | 新步骤面板，默认 100 m | 格子多大 |
| 制式 | 第④步面板选的制式 | 影响半径与后续聚类 |
| **链路余量** | **新步骤面板，默认 20 dB（v1.6 新增）** | 见下方"口径修正" |
| **扇区数** | **站点数据里的 `num_sectors`（第④步面板写入，默认 3）（v1.6 新增）** | 0=全向、N=N 扇区；决定要不要施加方向图损失 |

**输出**
- 一张栅格：每个格子一个 RSRP 值（dBm）；没信号的格子记 `-200` 作为哨兵值
- 栅格元数据：范围、分辨率、制式、频段、**链路余量（供报告做参数快照）**

**用到的现成零件**
`design_engine/coverage.py` 的 `okumura_hata_path_loss:6`（Okumura-Hata 路径损耗）、**`path_loss_with_directivity:78`（带天线方向性的路径损耗）**、`power_w_to_dbm:149`。**不自己写物理模型。**

> **🔴 v1.6 口径修正（这一节原本是错的，已重写）**
>
> **原来的算法**：`calculate_rsrp:55` 只预留了 8 dB 阴影衰落，天线增益**全额**计入（相当于假设"基站天线四面八方一样强"）。实测结果：演示场景三个频段的弱覆盖格**全是 0**，聚类 **0 片** —— 功能点下去图上什么都没有，"补盲"没有对象可找。
>
> **根因三条**（详见 02 文档 §0 R-13）：
> ① **没有链路余量** —— 干扰抬升、穿透损耗、边缘可靠性一概没算（教科书写法这三项合计 20~35 dB）；
> ② **把定向天线当全向算** —— 每站其实是 3 扇区、65° 波束，偏离主瓣方向实际要弱 3~15 dB（`path_loss_with_directivity` 里写着这个规则，但**全仓库从来没人调用过**，是"写了没装"的零件）；
> ③ **布局本身没有洞** —— 站点是按站间距均匀生成的，计算半径又比站距大，处处重叠。
>
> **改成什么**：
> ```
> RSRP = 发射功率(dBm) + 天线增益 − 扇区化路径损耗 − 8 dB 阴影衰落 − 链路余量(默认 20 dB)
> ```
> 逐站 × 逐扇区取最强。**扇区数不写死**，从站点数据的 `num_sectors` 读（缺该字段时回退 3 扇区）；读到 0（全向）就不施加方向图损失，改用不带方向性的路径损耗。
>
> **改完的实测对比**（12 站 / 2.6GHz / 5×5km / 默认参数）：
>
> | | 原算法 | 新算法 |
> |---|---|---|
> | 最低 RSRP | −80.4 dBm | **−113.4 dBm** |
> | 弱覆盖格 / 盲区格 | 0 / 0 | **340 / 8** |
> | 弱覆盖聚类 | **0 片** | **7 片** |
> | 可用覆盖率 | — | **86.1%** |
>
> **为什么会这样（一句话给评委）**：原来算的是"理论上信号能到多强"，现在算的是"实际能用上的信号有多强" —— 差了链路余量（干扰/穿透/边缘可靠性）和天线方向性两项，合计约 28 dB。
>
> ⚠️ **一个必须知道的设计取舍**：第⑦步的**热力图仍然用原口径**（不动它，避免波及既有功能）。所以第⑥步诊断与第⑦步热力图**有意不一致**，面板上会常驻一行口径说明，报告里也会写明。这是**批准过的设计**，不是 bug。
>
> ⚠️ **扇区数的敏感性**（实测，同一场景）：3 扇区 → 348 个弱格；6 扇区 → 39 个；8 扇区以上数字不再变。原因：65° 波束配 3 个扇区会留 3 个约 25° 的角向缺口，扇区多了缺口就没了。**演示时不要动面板的扇区数**（保持默认 3）。

**衔接**
上承**第⑤步「生成布局」**（站点在这一步才产生，诊断吃的就是它刚生成的那批站），下接环节 2。这是唯一一个"只看数据、不看地图"的环节，纯计算。

**怎么算做对了**
- 有站点的地方信号强、离站点越远越弱（符合常识）；
- **同一组站点换个频段/制式，结果能看到变化**（证明公式真的吃频段参数）；
- 全程**不连后端、不写数据库**，纯本地算。

### 环节 2｜标弱区（阈值分级）

**目标**
把栅格上"信号不够"的格子挑出来，并且分成两档：**弱覆盖**（还能用但很差）和**盲区**（基本没信号）。分级是为了地图上能一眼看出轻重。

**输入**

| 输入项 | 从哪来 | 默认值 |
|---|---|---|
| 环节 1 的栅格 | 环节 1 | — |
| 弱覆盖阈值 | 新步骤面板 | -100 dBm |
| 盲区阈值 | 新步骤面板 | -110 dBm |

**输出**
- 弱覆盖格集合、盲区格集合
- 统计数字：弱格数、盲格数、**可用覆盖率（%）**（定义见下方口径提醒）
- 地图图层「诊断 · 弱覆盖区」：弱覆盖半透明橙色、盲区半透明红色

**用到的现成零件**
`coverage.py:rsrp_to_color:156`（已有按阈值上色，默认阈值就是 -110）；热力图色带 `coverage_heatmap.py:style_coverage_heatmap:141` 里本来就有"弱覆盖/盲区"档位，配色沿用，不另起一套。

**衔接**
上承环节 1，下接环节 3。这是**第一个在地图上看得见东西**的环节 —— 演示时的第一个"哇点"。

**怎么算做对了**
- 被判为弱覆盖的格子，值**确实都低于阈值**（抽查几个能复核）；
- 阈值调高 → 弱覆盖面积**单调变大**；调低 → 变小。不能出现"'调严了面积反而变大'"这种反常识。

> ⚠️ **口径提醒（v1.6 更新）**：
> - 这一档 −100 / −110 是**分级线**（弱覆盖 / 盲区）；
> - 本功能输出的**「可用覆盖率」= RSRP ≥ 弱覆盖阈值（默认 −100 dBm）的格子占比** —— 与分级线**同一刻度**，因此三者严格互补：`可用覆盖率 + 弱覆盖占比 + 盲区占比 = 100%`（实测 86.1% + 13.6% + 0.3%）。
> - 插件里原来那个"覆盖率 ≥ −80 dBm"（覆盖分析弹窗 `_show_coverage_stats:4203`）是**达标线**，**本次不改**它。它是"优质覆盖"，数值会明显低于"可用覆盖率"，**两者不可直接比较**。
> - 界面上必须同时把这几句话摆出来（判据见 §九 风险表 R5）。

### 环节 3｜聚成片（聚类）

**目标**
把零散的弱格按位置**归堆**，把"一片一片"的弱覆盖区识别出来，并给每片算一个"有多急"的评分。不聚类的话，弱格是一盘散沙，没法对应到"在这儿补一个站"。

**输入**

| 输入项 | 从哪来 | 说明 |
|---|---|---|
| 弱覆盖格集合 | 环节 2 | — |
| 网格尺寸 | 自动按制式算 | `clamp(制式覆盖半径 ÷ 5, 100 m, 500 m)` |
| 最小栅格数 | 新步骤面板，默认 3 | 少于这么多格的片直接丢掉，滤掉碎片噪声 |

**网格尺寸随制式变化**（因为 5G 半径小，格子该更细）：

| 制式 | 覆盖半径 | 聚类网格 |
|---|---|---|
| 4G LTE | 2.0 km | 400 m |
| 4G+5G协同 | 0.5 km | 100 m |
| 5G NR(Sub-6) | 0.4 km | 100 m |
| 5G NR(mmWave) | 0.15 km | 100 m |

**输出**
一片一片的"弱覆盖区"，每片带：
- **质心坐标**（这片弱区大致在哪儿）
- **格子数**（这片有多大）
- **平均 RSRP**（这片有多差）
- **盲区格占比**
- **需求评分 0~100**（综合"面积 + 深度 + 盲区占比"三项算出，用来排序）

**用到的现成零件**
参考 `ftth/coverage_gap.py:_cluster_gap_sites:166` 的**算法骨架**（按米制网格分桶、算评分、取质心）。但那份是 FTTH 场景的判断逻辑，**判定条件整体换成 RSRP 栅格**，不能照搬。
它原来的评分权重是"缺口 0.5 / 投诉 0.3 / 路测 0.2" —— 因为本功能**不接投诉和路测数据**，这套权重直接作废，改用 RSRP 侧自己算得出的三项。

**衔接**
上承环节 2，下接环节 4。用户在这一步看到的仍然是地图（弱覆盖面），但后台已经把"片"切好了。

**怎么算做对了**
- 每一片**至少 3 个弱格**，不会出现孤零零一个格子算一片；
- 换制式，聚类粒度跟着变（4G 网格粗、5G 网格细）。

### 环节 4｜出建议站（选址）

**目标**
**每一片弱覆盖区，给一个"建议在这儿加个站"的候选点**，并在地图上标出来。这就是"选址"环节 —— 位置不是手点出来的，是算出来的、可解释的。

**输入**

| 输入项 | 从哪来 |
|---|---|
| 聚类结果（片 + 质心 + 评分） | 环节 3 |
| 制式 | 面板 |
| 频段 | 面板 |

**输出**
建议站列表，每条包含：

| 字段 | 取值来源 | 说明 |
|---|---|---|
| 建议站编号 | 自动生成 | 如 `SUG-补站-001` |
| 经度 / 纬度 | **聚类结果（片的质心）** | 保留 7 位小数 |
| 需求评分 | 聚类评分 | 0~100，用来排序 |
| 建议覆盖半径(km) | **制式基线** | 4G 2.0 / 5G Sub-6 0.4 / mmWave 0.15 / 协同 0.5 |
| 制式 | 面板 | 决定后续料单里的设备项 |
| 聚类栅格数 | 聚类结果 | 这片多大 |

另外在地图上生成一个独立图层「**诊断 · 建议补站**」：点的符号 + 评分标注，评分高的配色深。

**去重规则**：与已有正式站、以及本轮已生成的建议站，距离小于 **200 m** 的判为重复，合并时**保留评分高的那个**。

**用到的现成零件**
制式基线 `models/tech.py:get_baseline:69`；图层骨架参考 `ftth/coverage_gap.py:build_suggested_sites_layer:285` 的形态（换成蜂窝语义）。

### 环节 5｜采纳（建议站 → 正式站）

**目标**
把选中的建议站**一键转成正式站点**，让它进入站点表、出现在地图上，成为后续设计和出图的对象。这是"建议"变"方案"的那一下。

**输入**

| 输入项 | 从哪来 |
|---|---|
| 某条建议站（用户点"采纳"的那条） | 环节 4 |
| 站型 / 塔型 / 安装方式 / 塔高 / 场景 | 面板上的当前值 |

**默认属性**（可在面板调）：

| 属性 | 默认值 |
|---|---|
| 站型 | 宏站 MACRO |
| 塔型 | 单管塔 MONOPOLE |
| 安装方式 | 地面塔 GROUND |
| 制式 | 当前面板选的制式 |
| 覆盖半径 | 取制式基线 |

**输出**
- 站点集合多一条记录
- **13 列站点表**多一行（列结构不变）
- 地图上出现正式基站符号
- 自动在该站下方补一个机房（沿用现有逻辑，保证布线有终点）

**⚠️ 本功能最大的技术坑就在这一步**
站点数据有两套格式（`models/site.py:9` 的 dataclass 和界面用的裸字典），**采纳时必须两边都写全**：

- dataclass 侧要补齐：`site_id / name / longitude / latitude / site_type / tower_type / tower_height / mount_type / scenario / status / tech_generation / coverage_radius / capacity`

**为什么追加键是安全的**：现有读取这些字段的地方全部写成 `.get(键, 默认值)` 的形式（`_show_bom_dialog:6525` 一带动、`_export_report_xlsx:4378` 一带），多一个键不会改变任何现有行为。

**衔接**
上承环节 4，下接环节 6 和 7。

**怎么算做对了**
- 采纳后站点表**确实多了一行**，地图上**确实多了个点**；
- 对这个站出材料清单、导出报表，**不缺项、不报错**；
- **原有的 7 步流程一点都不受影响**（除了步骤编号顺延）—— 这是硬要求。

### 环节 6｜布线

**目标**

**输入**

**输出**

**用到的现成零件 —— 而且不需要写新代码**

第⑦步「管线·场景」已经有「生成管线」按钮（`_generate_pipelines:3662`），它第一句就是：

if not self.generated_sites:

**它是遍历整个站点池的。** 只要补的站在它之前进了 `generated_sites` —— 而这正是把新步骤放在**第⑤步之后**的收益 —— 用户走到第⑦步点一下「生成管线」，补的站**自动就被拉线了**。

**衔接**

**怎么算做对了**
- 采纳站到机房的线**画得出来**，且能绕开避让区；

### 环节 8｜出报告（补盲效果对比）

**目标**：把"补盲到底有没有用"变成一个**能交出去的文件**，而不是靠嘴说。

**输入**：
- 诊断时留下的基线快照（点诊断那一刻记下的四个数）
- 采纳后的站点集合（`generated_sites`）
- 面板参数（制式 / 频段 / 塔高 / 阈值 / 分辨率）
- 管线工程量（**若第⑦步已生成**；没生成就标"未生成"）

**输出**：一个 `.md` 文件，五段结构（补前补后对比 → 新增站点明细 → 新增工程量 → 参数快照 → 口径说明）。

**用到的现成零件**：
- `QFileDialog.getSaveFileName` + `_qsettings.value("report_dir")` —— `_export_report:4248` 的既有惯例，连"记住上次保存目录"都是现成的
- `calculate_coverage_rate`（`coverage.py:250`）算覆盖率
- 覆盖率与口径字符串**直接取 `diag.stats["coverage_rate_pct"]` / `diag.stats["coverage_caliber"]`**（v1.6 起由 `diagnose_weak_coverage` 一并产出），报告侧**不要自己拼口径文字**
- 渲染本身是**纯字符串拼接**，不引入任何新依赖

**衔接**：
- 上承：环节 5（采纳）之后的**任意时刻**；**不强依赖第⑦步**（没生成管线就把那一项标"未生成"）
- 下承：答辩 / 演示材料的量化依据（补盲前 vs 补盲后），也是 A8 的证据

**怎么算做对了**：
1. 四个核心数都有"补前 → 补后 → 变化"三列，且变化方向合理（**可用覆盖率↑**、弱区数↓）；
2. 新增站点明细表的条数 == 你实际采纳的站数；
3. 报告里**注明覆盖率口径与热力图的差异** —— 否则答辩被追问"你这覆盖率怎么跟热力图对不上"就麻烦了；
4. 哪怕你什么都没补就点导出，也**不报错**，而是给一份"仅补后状态"的报告并注明缺什么。

**第四个核心数 = 「可用覆盖率」**（v1.6 定案）：RSRP ≥ 弱覆盖阈值（默认 −100 dBm）的格子占比，与"弱覆盖 / 盲区"同一刻度，满足 `可用覆盖率 + 弱覆盖占比 + 盲区占比 = 100%`。实测演示场景补前 **86.1%**。
⚠️ **不要**在报告里用 ≥−80dBm 那个"达标线"数字 —— 新口径下它只有 11.3%，且第⑦步热力图同区是 100%，三个数字并排必被问。若想展示 −80 口径，只能放在第五段的"口径说明"里作为附注，且必须同时说明它与热力图的差异来源（约 28 dB 的余量 + 方向性）。

### 环节之间的衔接关系（汇总）

| 环节 | 上承 | 下接 | 中间传的是什么 |
|---|---|---|---|
| 1 算信号 | 第④步基站参数 | 2 | RSRP 栅格（格子 → dBm） |
| 2 标弱区 | 1 | 3 | 弱覆盖格 / 盲区格 集合 |
| 3 聚成片 | 2 | 4 | 弱覆盖区（质心 / 大小 / 评分） |
| 4 出建议站 | 3 | 5（人工确认） | 建议站列表 |
| 5 采纳 | 4 | 6、7 | 正式站点（两套格式都写全） |
| 6 布线 | 5 | 7 | 管线路由 + 工程量 |
| 7 材料清单 | 5 | 导出（报表/图册/CAD） | 物料清单 |

**一句话记住**：**1→2→3→4 是"算"，5 是"人拍板"，6→7 是"出成果"。**

## 八、明确不做（防止范围蔓延）

### 10.3 已锁定的默认值（v1.1 修正后）

- 聚类网格 = **实际布站间距**（按频段，`clamp(ISR×1000, 100, 2000)` m）—— 语义 = "一个站点的覆盖单元"尺度。700MHz→2000m／2.6GHz→1000m／3.5GHz→500m／4.9GHz→300m
- **最小弱区面积 = 聚类网格面积的 20%**（替代原"≥ 3 个栅格"，原值过松会让碎片成为独立聚类；也修掉了 v1.1 那个"永远不成立"的公式）
- **去重距离 = min(实际布站 ISR ÷ 2, 200 m)**（替代写死 200 m；写死会把 mmWave 的网格站全判为重复）
- 采纳默认：宏站 MACRO + 单管塔 MONOPOLE + 地面塔 GROUND + 当前制式 + 制式基线半径
- 诊断输入 = 现有全部站点（不含引擎候选站）
- 参数变了**手动**点重算，不自动刷新
