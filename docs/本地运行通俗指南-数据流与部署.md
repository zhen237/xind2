# 第一部分 · 这套系统到底在干嘛（5 分钟看懂）

## 1. 一句话

**它是一个通信基建工程从「有图纸」到「建完验收」的全流程平台。**

一条通信线路（埋光缆、建基站）要经过五道工序，对应五个子系统，**像接力赛一样一个传一个**：

```
S2 融合  ──▶  S1 设计  ──▶  S3 审查  ──▶  S4 清单  ──▶  S5 监控
把图纸变成     在地图上      按规范       算出要用      盯着施工
地图数据       画设计图      挑毛病       多少材料      进度

（注意顺序：S2 在最前面。名字带 S2 不代表排在第二道工序。）
```

## 2. 打个比方：盖房子

| 子系统 | 相当于 | 干的事 |
|---|---|---|
| **S2** 融合 | 把地勘图纸数字化 | 甲方给的 CAD 图纸，转成地图上能用的数据 |
| **S1** 设计 | 设计师出图 | 在地图上选站址、画管线、算覆盖范围 |
| **S3** 审查 | 审图员 | 拿着国家标准逐条检查：埋得太浅？弯曲半径不够？ |
| **S4** 清单 | 算料员 | 根据设计图算出要买多少光缆、多少设备（BOM 清单） |
| **S5** 监控 | 工地监理 | 记录施工进度，核对实际做了没有 |

## 3. 数据是怎么一环扣一环流下去的

下面这张图是**真正在跑的链路**（不是示意图，接口路径都来自代码）：

```
① 甲方 CAD 图纸（.dwg / .dxf）
        │
        ▼  上传
   ┌─────────────────────────────────────────────────────┐
   │ S2 融合  （后端 8096 · 前端 5182 · 引擎 8092）        │
   │  · 原始文件落磁盘  uploads/cad/                       │
   │  · 登记一条记录到 MySQL 表  s2_cad_file               │
   │  · 交给 Python 引擎解析 → 坐标转换 → 融合             │
   │  · 产出 GeoJSON：落磁盘 uploads/output/{任务id}.geojson│
   │    同时拆成一条条要素写进 MySQL 表  s2_gis_feature     │
   └──────────────────────┬──────────────────────────────┘
                          │ 推给 S1
                          ▼
   ┌─────────────────────────────────────────────────────┐
   │ S1 设计  （后端 8083 · 前端 9000 · 引擎 9001）        │
   │  · 接数据有两条路（下节细说）                          │
   │  · 点「执行设计」→ 算设备布局 + 覆盖范围               │
   │  · 成果落 MySQL 表  m03_design_task.result_json       │
   └──────────────────────┬──────────────────────────────┘
                          │ 执行成功后【自动】推送，不用手动操作
                          ▼
   ┌─────────────────────────────────────────────────────┐
   │ S3 审查  （后端 8089 · 前端 5189 · 引擎 8000）        │
   │  · 收到设计数据，存 s3_review_task / s3_design_data    │
   │  · 交给规则引擎跑 25 条规范检查                        │
   │  · 结果落 MySQL 表  s3_review_result                  │
   └──────────────────────┬──────────────────────────────┘
                          │ S4 【主动去拉】（不是 S3 推的）
                          ▼
   ┌─────────────────────────────────────────────────────┐
   │ S4 清单  （后端 8090 · 前端 5190 · 引擎 8100）        │
   │  · 调 BOM 引擎算料                                    │
   │  · 结果落 s4_bom_task / s4_bom_item，可导出 Excel     │
   └──────────────────────┬──────────────────────────────┘
                          │ 推给 S5
                          ▼
   ┌─────────────────────────────────────────────────────┐
   │ S5 监控  （后端 8091 · 前端 5191）                    │
   │  · ⚠️ 它没有数据库！数据直接写磁盘 JSON 文件           │
   │    backend/data/verify-tasks.json（已被 gitignore）   │
   │  · 也不用 Redis。它是全平台最轻的一个模块              │
   └─────────────────────────────────────────────────────┘
```

**S5 的全部接口**（它真的很小，只有 6 个）：

| 接口 | 用途 |
|---|---|
| `GET /api/s5/health` | 健康检查 |
| `GET /api/s5/dashboard` | 监控看板 |
| `GET /api/s5/devices` / `GET /api/s5/devices/:code` | 设备列表 / 单个设备 |
| `GET /api/s5/alerts` | 告警列表 |
| **`POST /api/s5/verify/tasks`** | **S4 推过来的施工审核任务落在这里** |
| `GET /api/s5/verify/tasks` | 读回审核任务 |

> **S5 的接口不加鉴权**（它不连 m01），本地直接访问就能通。
> 这一点和别的模块不一样，别以为是自己漏配了 token。

**记住两个跟直觉不一样的地方**：

1. **S1 → S3 是自动的**：你在 S1 点完「执行设计」，只要成功，S1 会立刻把结果推给 S3。你不需要去 S3 点导入。
2. **S3 → S4 是 S4 主动去拉的**（不是 S3 推的）。所以 S4 要配好 S3 的地址。

## 4. S1 接数据的两条路（新手最容易懵的地方）

S1 是整个平台的**心脏**，也是最容易出问题的地方。它接数据有两条路：

| 路线 | 接口 | 什么时候用 | 注意 |
|---|---|---|---|
| **A. 网页上传** | `POST /api/m03/design/upload` | 数据在中国境内时 | ⚠️ **只接受中国境内坐标**（经度 73–135、纬度 3–54）。境外坐标会被**静默丢掉**，不报错！ |
| **B. 灌入本地数据** | `PUT /api/m03/design/tasks/{任务id}/local-data` | **QGIS 插件出的 GeoJSON 走这条** | 唯一的正确用法，见下面 |

> **为什么 QGIS 出的图不能走 A 路线？**
> 因为插件做的是境外项目（摩洛哥），坐标不在中国的经纬度范围内，走上传接口会被全部丢掉，
> 结果就是「传上去了，但一个站点都没有」，而且**页面不会报错**。
> 正确做法是：先建一个空任务，再把原始 GeoJSON 原文塞进去。

**建任务时注意**：`POST /api/m03/design/tasks` 的 `paramsJson` 字段是**必填**的，别漏。

### 4.1 一张设计任务表里有三个 JSON 字段，别搞混

这是本项目最高频的困惑点。`m03_design_task` 表里同时存着三种数据：

| 字段 | 存的是 | 什么时候用 |
|---|---|---|
| `params_json` | 你填进去的**参数**（设计几个站、站高多少、什么频段…） | 任务创建时写入 |
| `result_json` | 系统算出来的**完整成果**（站点 + 机房 + 馈线 + 覆盖） | 展示成果时用。⚠️ 但它**只带站点信息**，会丢机房/馈线/路由类型 |
| `local_data_json` | QGIS 出的**原始 GeoJSON 原文**（顶层有 `machine_rooms` / `cables` / `pipeline` / `route_type`） | **有它的时候优先用它**，因为它最全 |

**记住这条规则**：前端页面显示成果时，**只要 `local_data_json` 有值，就优先读它**。这样机房、馈线这些才不会丢。

### 4.2 一份真实样本长什么样

这是 QGIS 插件实际产出的一份文件（`design_20260913.geojson`，2026-09-13 导出，摩洛哥项目），
**它的结构就是 `local_data_json` 的结构**，提前看懂能省很多时间：

```
{
  "type": "FeatureCollection",
  "features": [ ... 6 个要素，全是 Point（就是 6 个基站站点） ... ],
  "properties": {          ← ★ 重点：数据其实在这里，不在 features 里！
      "band": "3.5GHz",
      "tower_height": 35,
      "route_type": "optimal",      ← 路由类型（最优）
      "machine_rooms": [ ... 6 条机房 ... ],
      "cables":        [ ... 6 条馈线 ... ],
      "pipeline":      [ ... 6 条管线 ... ],
      "has_ftth": false,
      "ftth_stats": null,
      "saved_at": "2026-09-13T19:46:27"
  }
}
```

**⚠️ 这里有个大坑**：`features` 数组里**只有基站站点**。
机房、馈线、管线全在 **顶层 `properties`** 里。

所以如果哪个环节只读了 `features`、没读顶层 `properties`，**结果就是「只有基站，机房和连线全不见了」**。
这就是上面说的「`result_json` 只带站点会丢数据」的具体表现——不是玄学，是字段没读全。

一个基站要素本身长这样（字段相当全）：

```json
{ "type": "Feature",
  "geometry": { "type": "Point", "coordinates": [-8.5359125, 33.2134738] },
  "properties": {
      "site_id": "BTS-URBA-006", "name": "URBAN-006",
      "longitude": -8.5359125, "latitude": 33.2134738,
      "tower_height": 35.0, "site_type": "MACRO", "num_sectors": 3,
      "scenario": "URBAN", "band": "3.5GHz", "frequency": 3500,
      "coverage_radius": 0.5, "served_room_id": "ROOM-BTS-URBA-006",
      "groundingResistance": 4.0, "bearingCapacity": 250.0, "designLoad": 180.0
  }
}
```

> **注意那几个工程字段**（`groundingResistance` 接地电阻 / `bearingCapacity` 承载 / `designLoad` 设计荷载）——
> 它们正是 **S3 审查规则**要检查的输入。这就是「S2/S1 的数据要能喂给 S3」的实际含义。

### 4.3 点「执行设计」的时候，系统走哪条路？

代码里 `DesignService.executeDesignTask()` 会做个判断：

```
点了「执行设计」
      │
      ├── local_data_json 有值 ──▶ 直接拿你灌进去的真实数据搭方案（不画网格）
      │
      └── local_data_json 是空的 ─▶ 调拓扑引擎 http://localhost:9001/generate
                                    算出设备布局 + 覆盖率
```

> **🔴 引擎没起，系统不会报错。**
> 它会**偷偷改用本地后备算法**，画一片规规矩矩的六边形网格，只在后端日志里留一行警告。
> **怎么判断中招了**：成果看起来「太整齐、像键盘格子」而不是「像真实选址」，那就是回退了。
> 排查：确认 `http://127.0.0.1:9001/health` 是通的。

## 5. 数据到底存在哪（存哪儿总表）

新手最常问的就是这个。一张表说清楚：

| 数据 | 存在哪 |
|---|---|
| 用户 / 角色 / 菜单 / 权限 | MySQL `comm_platform` 库（`m01_*` 开头的表） |
| 设计任务 / 设计方案 / 站点 | MySQL（`m03_design_task` / `m03_design_scheme` / `m03_site`） |
| CAD 原始文件 | **磁盘** `uploads/cad/` |
| 融合后的地图要素 | **磁盘** `uploads/output/*.geojson` **+** MySQL `s2_gis_feature` |
| 审查任务 / 设计数据 / 审查结果 | MySQL（`s3_review_task` / `s3_design_data` / `s3_review_result`） |
| BOM 任务 / 清单条目 | MySQL（`s4_bom_task` / `s4_bom_item`） |
| 施工审核任务（S5） | **磁盘 JSON 文件**：`packages/s5-construction-monitor/backend/data/verify-tasks.json`（该目录已在 `.gitignore` 里，不会提交） |
| 各类缓存 | Redis（m03 缓存模板/区域/机型/设计方案；s3 缓存设计数据） |
| 上传的图片 | **本地磁盘** |
| 表结构版本记录 | MySQL 里**每个模块一张** `flyway_schema_history_<模块名>` |

**一句话总结**：**MySQL 存业务数据，Redis 存缓存，上传的文件都在本地磁盘上。**

另外，后端第一次启动时会**自动建表**（Flyway 迁移），你不需要手工执行任何 SQL。

### 5.1 三个「你以为要用、其实根本没用」的东西

项目文档里提到过这些名字，但它们**在代码里并没有真正接上**。本地调试**不要为它们花时间**：

| 组件 | 状态 | 说明 |
|---|---|---|
| **MinIO**（对象存储） | ❌ 没接 | 只在 `pom.xml` 里有依赖，代码里**一次都没有调用**。上传的文件全在本地磁盘。**不用装** |
| **InfluxDB**（时序数据库） | ❌ 没接 | 只在 `docker-compose.yml` 里写了定义，代码里没有连接。**不用装** |
| **EMQX / MQTT** | ⚠️ 半截 | 只有 m05 订阅了 `/device/+/alert` 主题，**但仓库里没有任何地方发消息**。本地不装也不影响 |

# 第二部分 · 在本地跑起来（照着做）

## 6. 先有个心理准备：要开多少个窗口

这是新手最容易被打败的地方——**不是一个前端点开就能用**。

打开 S1 页面时，背后**至少有 4 样东西必须在跑**：MySQL、Redis、m01 认证服务、m03 设计服务。少一个，页面要么转圈要么报错。

完整跑起来需要的窗口数量：

| 类别 | 数量 | 必需吗 |
|---|---|---|
| MySQL | 1（Windows 服务，不用开窗口） | ✅ 必需 |
| Redis | 1 个窗口 | ✅ 必需 |
| Java 后端 | 8 个窗口（通常够用只开 m01 + m03） | m01/m03 必需，其余按需 |
| Python 引擎 | 5 个（通常只开拓扑引擎 9001） | S1 出真实设计成果必需 |
| 前端 | 7 个（通常只开 m03 那个） | 按需 |
| QGIS | 1 个（桌面程序） | 只用 Web 端可以不装 |

> **别一口气全开。** 建议分三档，跑通一档再上一档（见 §7）。

## 7. 三档目标，你自己选

| 档位 | 目标 | 需要起什么 | 适合谁 |
|---|---|---|---|
| **第 1 档** | 看到 S1 页面 + 三维地球 | MySQL、Redis、m01、m03、S1 前端 | 只想先看看长什么样 |
| **第 2 档** | S1 能出**真实**设计成果 | 第 1 档 **+ 拓扑引擎 9001** | 要验证设计功能 |
| **第 3 档** | 全流程跑通 | 再加 s2 / s3 / s4 / s5 及其引擎 | 要验证数据流、要做集成测试 |

**⚠️ 第 2 档不要跳。** 少了拓扑引擎，S1 会静默降级（见 §4.3），你以为跑通了，其实成果是假的。

## 10. 起后端

### 10.1 第一步：先构建 shared（只做一次）

`shared` 是所有模块共用的公共库，**必须先装到本地**，否则后面每个模块都编译不过：

```bash
cd packages/shared/backend
mvn install -DskipTests
```

看到 `BUILD SUCCESS` 即成功。

> **🔴 铁律：Maven 必须在模块自己的目录里执行。**
> 不要用 `mvn -f D:/xxx/pom.xml` 这种写法——在本项目上会报「POM 不存在」或 `classworlds` 错误。

### 10.2 启动 Java 后端（每个开一个窗口）

以 m03 为例：

```bash
cd packages/m03-bim-gis/backend
mvn spring-boot:run -Dspring-boot.run.arguments="--server.port=8083"
```

**第 1 档只需要 m01 和 m03 两个**（m01 换成 `packages/m01-auth/backend`、端口 `8080`）。

**怎么知道起没起来**：

| 模块 | 验证地址 | 通过标准 |
|---|---|---|
| m03 | `http://localhost:8083/api/m03/health` | 响应体里有 `"status":"UP"` |
| m01 | `http://localhost:8080/api/m01/user` | **返回 401 或 403** |

> **⚠️ m01 没有 health 接口**（它只有 auth / menu / user 三个控制器）。
> 所以**能返回 401/403 就说明服务活着**；显示「无法访问」或 500 才是没起来。

> **⚠️ 看到 401 / 403 别慌，那是正常的**，说明鉴权拦住了，服务本身是活的。
> 真正要警惕的是 **500**（服务内部报错）和**打不开**（没起来）。

> **⚠️ 接口返回是「包了一层」的**：Java 后端统一用 `Result` 包装，长这样
> ```json
> {"code":200,"message":"操作成功","data":{"status":"UP",...}}
> ```
> 所以 m03 health 看到的**不是**裸的 `{"status":"UP"}`。
> **更重要的是**：业务出错时它可能返回 **HTTP 200，但 body 里 `code` 是 500**。
> 所以**判断成功不能只看 HTTP 状态码，要看 body 里的 `code`**。

### 10.3 s2 的端口要特别处理

`s2` 的配置文件里默认写的是 `8082`，但团队约定**本地一律用 8096**：

```bash
cd packages/s2-cad-fusion/backend
mvn spring-boot:run -Dspring-boot.run.arguments="--server.port=8096"
```

前端的代理已经指向 8096，你不用改前端。

### 10.4 S5 后端不是 Java（别用 mvn）

`packages/s5-construction-monitor/backend` 是个 **Node.js 项目**，没有 `pom.xml`：

```bash
cd packages/s5-construction-monitor/backend
npm install
PORT=8091 node src/server.js
```

> **顺带说一句**：`packages/m07-cv-engine` 目前是**空骨架**（只有 README 和几个空目录，没有任何 `.py`）。
> **它跑不起来、也不需要跑**——这是已知状态，不是你的环境坏了。

## 11. 起 Python 引擎

### 11.1 为什么每个引擎都要单独的虚拟环境

5 个引擎对依赖版本的**要求互相冲突**（比如 s4 引擎要 `fastapi` 低于 0.110，而 m03/s3 锁定 `0.115.0`）。
装一起必然有一个跑不起来。所以**一个引擎一个 `.venv`**，这是硬要求。

### 11.2 引擎清单

| 引擎 | 目录 | 端口 | 模块名 | 第几档需要 |
|---|---|---|---|---|
| **拓扑引擎** | `packages/m03-topology-engine` | **9001** | `main:app` | **第 2 档起必须** |
| S2 CAD 融合引擎 | `packages/s2-cad-fusion/engine` | 8092 | `cad_engine.server:app` | 第 3 档 |
| S3 规则引擎 | `packages/s3-review-engine/rules` | 8000 | `main:app` | 第 3 档 |
| S4 BOM 引擎 | `packages/s4-bom-transform/engine` | 8100 | `main:app` | 第 3 档 |
| m03 LLM 服务 | `packages/m03-llm-service` | 9002 | `main:app` | 不用起 |

### 11.3 启动（以拓扑引擎为例）

```bash
cd packages/m03-topology-engine
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m uvicorn main:app --host 127.0.0.1 --port 9001
```

其余引擎：换目录、换端口、换模块名，命令完全一样。

> **不要用 `source .venv/bin/activate` 或 `.venv\Scripts\activate`**。
> 有时它改了环境变量，但 `python` 仍然指向系统 Python，结果报 `No module named uvicorn`。
> **直接写 `.venv/Scripts/python.exe -m uvicorn ...` 最稳。**

**验证**：

```bash
curl http://127.0.0.1:9001/health    # 期望 {"status":"ok",...}
```

## 13. 装 QGIS 插件

### 13.1 用「目录链接」而不是「复制文件」

QGIS 只会去它自己的插件目录找插件。**推荐建一个目录链接（junction）指回仓库**——这样你改仓库代码，QGIS 立刻能看到，**永远不会有「两份代码不一致」的怪问题**：

```bash
cmd //c mklink /J "C:\Users\<你的用户名>\AppData\Roaming\QGIS\QGIS3\profiles\default\python\plugins\qgis-plugin-complete" "D:\你的路径\xind2\qgis-plugin"
```

> **为什么不推荐复制**：仓库里那个 `scripts/sync-qgis-plugin.ps1` 是**复制**文件的，
> 而且里面**硬编码了原作者的绝对路径**。直接跑它会把文件复制到你想不到的地方。
> 真实教训：开发目录和 QGIS 目录各存在一份，改了 A 却加载的是 B，排查了很久。

### 13.2 装依赖（一定要装到 QGIS 自带的 Python）

在 QGIS 菜单里打开 **插件 → Python 控制台**，粘贴执行：

```python
import subprocess, sys
subprocess.check_call([sys.executable, "-m", "pip", "install", "dbfread", "pyshp", "numpy", "requests"])
```

> 报 **`No module named pip`** 的话，先执行 `import ensurepip; ensurepip.bootstrap()` 再重试。

验证：

```python
import dbfread, shapefile, numpy, requests
print("依赖 OK")
```

### 13.3 启用插件

1. **重启 QGIS**
2. **插件 → 管理和安装插件 → 已安装**
3. 勾选 **「通信基站智能设计平台」**
4. 界面上出现左侧的**步骤向导面板** = 装好了

### 13.4 改了插件代码怎么生效

**只重启 QGIS 不够**（Python 会缓存模块）：

1. 插件 → **卸载插件** → 再**重新启用**
2. 还不行就删掉插件目录下所有 `__pycache__` 文件夹
3. 再重启用

### 13.5 底图需要联网

插件的底图是在线瓦片（Esri 卫星影像 / OpenStreetMap / 天地图）。

> **断网状态下没有底图，只能看到一个空地球——这不是 bug。**
> 部分内网/校园网连不上 Esri 或 OSM，表现是底图灰掉。

### 13.6 插件怎么跟 Web 端连起来

插件设计完，可以把成果**同步到 m03 后端**，然后在 S1 网页上看到：

```
QGIS 插件（设计+导出）──同步──▶ m03 后端 :8083 ──▶ S1 网页 :9000/modules/m03/
```

插件读两个环境变量（定义在 `qgis-plugin/ui/design_dock.py:284`）：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `M03_API_URL` | `http://localhost:8083` | 默认就指向本机，本地开发**不用设** |
| `M03_API_KEY` | `CHANGE_ME` | 内部接口鉴权密钥，本地保持默认 |

**前提**：m03 后端必须在跑。同步失败时，弹窗会告诉你它在连哪个地址，先核对是不是 `http://localhost:8083`。

## 14. 三条「看着跑通了、其实没通」的坑

这是本项目最容易误判的地方。**排查问题前先排除这三种。**

### 坑 1：拓扑引擎没起，系统偷偷用了后备算法

- **现象**：设计任务能跑、页面也有结果，但产出不对劲（本该是真实的 6 个站点，变成一片整齐的网格）
- **原因**：后端连不上引擎时**静默回退**到本地算法，只在日志里留一行警告，**不弹错**
- **怎么办**：先确认 `http://127.0.0.1:9001/health` 是通的；去 m03 后端日志搜「回退」/`degraded`

### 坑 2：浏览器里的旧草稿把真实数据顶掉了

- **现象**：明明改了数据，刷新后还是老的
- **原因**：S1 页面把编辑状态存在浏览器 localStorage（键名 `m03_ai_design_draft`），重开时**自动恢复草稿**
- **怎么办**：F12 → Application → Local Storage → 删掉 `m03_ai_design_draft`，然后**硬刷新**（`Ctrl + F5`）

### 坑 3：HTTP 是 200，但业务其实失败了

- **现象**：接口「成功」返回，页面还是报错
- **原因**：Java 后端的业务错误**包在 body 里**（HTTP 200 但 `code` 是 500）
- **怎么办**：**别只看 HTTP 状态码**，F12 看响应体里的 `code` 和 `message`

## 15. 最有说服力的验证：亲手走一遍完整数据流

前面都是「每个服务活着吗」。这一步是**验证它们真的串起来了**——也是第一部分那张图的实际演练。

**前置**：第 2 档跑起来（MySQL + Redis + m01 + m03 + 拓扑引擎 + S1 前端）。

| 步 | 做什么 | 期望结果 |
|---|---|---|
| 1 | 打开 `http://localhost:9000/modules/m03/` | 看到三维地球 + 左侧面板 |
| 2 | 清掉旧草稿（见 §14 坑 2） | Local Storage 里没有 `m03_ai_design_draft` |
| 3 | 用 QGIS 插件出一份 GeoJSON，或直接用现成的 `design_20260913.geojson` | 文件在手 |
| 4 | 走 **B 路线**灌进去：先 `POST /api/m03/design/tasks`（**记得填 `paramsJson`**）建任务，再 `PUT /api/m03/design/tasks/{id}/local-data` 把 GeoJSON 原文塞进去 | 两次都返回 `code: 200` |
| 5 | 在页面上打开这个任务，点**查看成果** | 地图上出现**基站点位 + 机房点位 + 连线** |
| 6 | 点**执行设计** | 返回成功，成果落 `m03_design_task.result_json` |
| 7 | 去看 **m03 后端日志** | **没有**「回退」/`degraded` 字样（有 = 引擎没起作用，回 §14 坑 1） |
| 8 | 起 s3（8089 + 规则引擎 8000），再执行一次设计 | S3 的 `s3_review_task` 表里**多了一条记录**（说明 S1→S3 自动推送成功） |
| 9 | 起 s4（8090 + BOM 引擎 8100），在 S4 里按 S3 任务 id 拉取结果 | `s4_bom_task` + `s4_bom_item` 有数据，能导出 Excel |
| 10 | 起 s5（8091），在 S4 触发推送 | `packages/s5-construction-monitor/backend/data/verify-tasks.json` 里出现这条任务 |

**第 8 步是关键**：它验证了「S1 自动推 S3」这条链路，这是平台上最容易断的一环——因为它是**自动**发生的，断了不会有人去点「导入」，就静悄悄地没数据。

**第 4 步是最容易失败的一步**：灌数据时 `data` 字段里要放 **`design_20260913.geojson` 的完整原文**（整个文件内容，不是文件路径）。
塞错格式会静默失败，页面看起来像「成功但没数据」。

> **用团队共享的摩洛哥样例数据**（文件名 `design_20260913.geojson`，向组长索取）时，
> 第 5 步应该能看到 **6 个基站**，以及 **6 个机房**（每个机房在自己的基站正下方）、**6 条馈线 + 6 条管线**。
>
> **如果你只看到 6 个基站、没有机房和连线，那就是页面只读了 `features`、没读顶层 `properties`**（回 §4.2 看结构）。
> 这不是你的环境问题，是数据读取链路的已知风险点。
