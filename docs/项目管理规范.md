## 一、任务优先级管理

### 1.1 优先级定义

| 等级 | 标识 | 说明 | 处理时限 |
|------|------|------|----------|
| **P0** | 🔴 紧急 | 安全漏洞、核心功能故障、阻碍项目发布 | 24小时内 |
| **P1** | 🟠 重要 | 性能问题、UX 缺陷、影响开发效率 | 3天内 |
| **P2** | 🟡 一般 | 代码清理、文档优化、非核心改进 | 1周内 |
| **P3** | 🟢 低 | 技术债务、远期规划 | 按需安排 |

### 1.2 判断标准

**P0 - 紧急**: 安全漏洞（认证绕过、敏感信息泄露）、核心功能故障（系统无法启动、数据丢失）、阻碍发布（编译错误、依赖冲突）

**P1 - 重要**: 性能问题（N+1查询、内存泄漏）、UX 问题（页面卡顿、交互异常）、代码质量（重复代码、架构不合理）

**P2 - 一般**: 文档优化、代码清理、配置优化、UI 细节

**P3 - 低**: 技术债务清理、新技术调研、远期架构演进

### 1.3 资源分配

| 优先级 | 资源占比 | 策略 |
|--------|----------|------|
| P0 | 100% | 所有可用资源优先处理 |
| P1 | 60% | 主要开发资源投入 |
| P2 | 30% | 次要资源投入 |
| P3 | 10% | 空闲时间处理 |

### 1.4 流转机制

- **每周评估**: 每周一调整任务优先级
- **紧急插入**: P0 任务可随时插入，暂停当前 P2/P3
- **延期升级**: 超过处理时限的任务自动升级优先级

### 1.5 变更审批

| 变更 | 审批人 |
|------|--------|
| P0 ↔ P1 | 技术负责人（王） |
| P1 ↔ P2 / P2 ↔ P3 | 模块负责人 |
| P1 → P0 | 技术负责人 + 项目负责人（高） |

## 二、文档复查机制

### 2.1 复查频率

| 文档类型 | 周期 | 触发条件 |
|----------|------|----------|
| **核心文档**（INDEX/PROJECT-OVERVIEW/分工方案） | 每月 | 每月1日 |
| **技术文档**（架构规范/数据库/API） | 每季度 | 接口或表变更后立即复查 |
| **子赛题规格文档** | 每次赛题开发阶段开始时 | 新模块创建时 |
| **全部文档** | 每半年（1月/7月） | 年度审计 |

### 2.2 责任人

| 角色 | 负责人 | 职责 |
|------|--------|------|
| 文档管理员 | 高 | 月度复查、更新记录、通知结果 |
| 技术负责人 | 王 | 季度复查、审核技术文档 |
| 项目负责人 | 高 | 半年复查、协调资源 |

### 2.3 复查检查清单

**通用检查项**:
- [ ] 版本号和更新日期完整
- [ ] 变更记录章节存在
- [ ] 文档内链接有效
- [ ] 术语全文一致
- [ ] 内容与代码一致

**文档问题严重程度**:

| 等级 | 定义 | 处理时限 |
|------|------|----------|
| P0 | 信息错误导致系统异常或安全风险 | 24小时 |
| P1 | 信息不准确影响开发效率 | 3天 |
| P2 | 格式问题、术语不统一 | 1周 |

### 2.4 复查流程

```
通知（提前3天） → 检查（复查当天） → 评估严重程度 → 分配修复 → 执行修复 → 验证 → 更新记录
```

### 2.5 AI 辅助检查清单

| 检查项 | 搜索关键词 | 风险 |
|--------|------------|------|
| 硬编码密码 | `password:.*[^$]` | 🔴 高 |
| 权限绕过 | `anyRequest().permitAll()` | 🔴 高 |
| 跨域风险 | `targetOrigin.*\*` | 🔴 高 |
| 内存泄漏 | `Cesium\.Viewer` 无 destroy | 🟡 中 |
| SQL注入 | `String.format` + SQL | 🔴 高 |
