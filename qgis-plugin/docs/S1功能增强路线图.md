## 1. 基站选址逻辑优化 —— 结合投诉/路测数据

- **现状**：`ftth/coverage_gap.py` 的 `analyze_coverage_gap` 只做纯几何判断——用 ZNRO/ZPM 覆盖区面 `contains` 每个 IMB 楼栋，缺口楼栋按 400m 网格聚类，质心即"建议站点"。**完全没有投诉点、路测弱覆盖这类"真实需求"输入**。
- **目标**：把弱覆盖证据（用户投诉热点、路测 RSRP/RSSI 弱覆盖网格）纳入选址评分，让建议站点落在真实需求最密集处，而非仅几何盲区。
- **做法**：
  1. 在 ③ 覆盖缺口步骤新增「生成演示投诉/路测数据」按钮——在**已加载 IMB 楼栋的同一坐标系**内合成投诉点(红)+ 路测弱覆盖面(半透明红)，确保必然叠加（绕开 FTTH 真实数据"prj 谎称 4326、坐标实为投影网格"的脏数据坑）；真实数据到位后，把同名 `COMPLAINT`/`ROADTEST` 图层替换即可，无需改代码；
  2. 选址评分 = `缺口楼栋数 × w1 + 簇内投诉点数 × w2 + 路测弱覆盖占单元比 × w3`（w1/w2/w3 在 UI 可调，默认 0.5/0.3/0.2）；
  3. 质心按"加权需求方向"偏移（投诉/弱覆盖越密拉得越狠，封顶 0.6），输出带 `demand_score` 的建议站点并标注需求分。
- **进度**：核心已实现（`coverage_gap.analyze_coverage_gap` 加 `weights` + 需求评分/质心偏移；`design_dock` 加权重微调 + 演示数据生成按钮 + 标注需求分），`py_compile` 通过，待 QGIS reload 验证。
- **工作量**：中（需定义数据格式 + 评分函数 + UI 入口）
- **风险**：需样例投诉/路测数据；权重需校准，否则建议点会偏移过度。

## 2. 管线设计精细化 —— 成本最优 + 区分光纤类型

- **现状（2026-08-13 已落地）**：`design_engine/pipeline.py`
  - `optimize_pipeline_route` **已重写为网格 Dijkstra**（8 邻接、边权=段长+避让惩罚，cell≈25m、max_nodes≈6000、penalty≈8；自适应经纬度/投影米，无 shapely 时安全降级"不避让"，全程 try/except 回退曼哈顿），不再是占位曼哈顿；
  - 新增 `FiberType` 枚举（G.652D / G.657A / 微型光缆）+ `PipelineConfig.fiber_cost_configs`，**光缆按类型取价**（示意单价：G.652D 12 / G.657A 18 / 微型 25 元/m，待校准），取代原固定 15/18。
- **目标**：路由搜索以综合成本（材料 + 施工 + 避让代价）为目标；光缆按类型取不同单价，自动选便宜合规的组合降本。
- **做法**：
  1. 成本函数接入网格 Dijkstra（节点代价 = 该段敷设方式成本，边代价含避让惩罚）；
  2. `cost_configs` 增加光纤类型维度（G.652D / G.657A / 微型），单价差异化；
  3. 工程量与成本报表按「管线类型 × 光纤类型」二维拆分（`calculate_total_cost` 增 `fiber_costs` 与 `cross_costs`，文本/CSV 均含「光纤类型」列）。
- **进度**：核心已实现并拆分四层——`models/pipeline.py`（FiberType 枚举 + Pipeline 字段 + 序列化 + fiber_cost_configs）、`design_engine/pipeline.py`（Dijkstra 路由 + 成本二维取价 + 报表）、`ui/design_dock.py`（光纤类型下拉 + 路由方式三选一：直线/曼哈顿/成本最优；GeoJSON 导出保留 optimal 真值，后端同步降级为 manhattan 保兼容）、`route_type` 协议 `{0:direct,1:manhattan,2:optimal}`。`py_compile` + 离线逻辑自测全通过（往返一致、单价 12/25 校验、Dijkstra 三模式不崩溃、报表二维产出），待 QGIS reload 验证。
- **工作量**：中偏大（路由算法重写 + 回归测试）
- **风险**：离线无 shapely 已做安全降级；单价表为示意值需行业参考值校准；后端同步已对 optimal 降级，不破坏现有演示。

## 3. 塔型区分功能 —— 地面塔/楼面塔 + 精确物料清单

- **现状**：`models/site.py` 有 `tower_type`（MONOPOLE/LATTICE/TOWER）和 `tower_height`；站型有 MACRO/SMALL/INDOOR；**缺"安装方式=地面塔/楼面塔"维度**。BOM 提取器 `extractors/`（塔桅/天馈/电源/机柜/接地）已有雏形。
- **目标**：增加「地面塔（落地基础）/ 楼面塔（楼顶抱杆/美化天线）」判断，据此生成精确物料清单——地面塔计基础浇筑+接地网，楼面塔计抱杆+承重+防水。
- **做法**：
  1. `Site` 模型加 `mount_type` 字段；
  2. `station_dialog.py` 加下拉；图层/同步 JSON 透传该字段；
  3. `extractors/` 按 `mount_type` 分支输出物料清单。
- **工作量**：中（BOM 已有基础）
- **风险**：低

## 4. 机房与基站关联简化 —— 基站下方直接标注机房

- **现状**：已实现橙色虚线关联线（`_draw_ftth_room_connectors`，一机房连最近锚点），用于表达 FTTH↔机房 归属。
- **目标**：基站符号下方直接标注归属机房名，**不再单独绘制关联线/图层**，减少画面 clutter。
- **做法**：
  1. 基站渲染时在其符号下方加标签（机房名，来自 `served_room_id` / 命中半径）；
  2. 提供开关：在「标注模式 / 连线模式」间切换，保留关联线能力。
- **工作量**：小
- **风险**：低

## 5. 设计场景分类 —— 全新建站 / 线网补盲 + 通信技术维度（4G/5G）

- **现状**：`design_dock.py` 已有「建设模式」开关（`现网补盲 brownfield` / `新区新建 greenfield`），但 **greenfield 标着"规划中"、FTTH 自动生成未接入、第②③步禁用**——只做了一半。且**完全没有"通信技术制式"维度**：4G/5G 的覆盖半径、频段穿透/绕射、站间距、单站容量、塔桅形态都不同，但目前一刀切。
- **目标**：把"设计场景"拆成 **二维**——
  - 范式轴：补盲（加载现网→找缺口→缺口处补设施）/ 新建（空地起建→建机房→铺管线→FTTH 自动生成→基站挂接）；
  - **技术轴（新增）**：按 4G / 5G / 多制式共存 选择，驱动覆盖半径、建议站点间距、单站容量、BOM 形态等参数。
- **做法**：
  1. greenfield 真正接入 FTTH 设计生成器（OLT 落机房、光缆走管线），步骤指引/禁用逻辑按范式分两套；
  2. 新增"技术制式"选择（4G / 5G / 4G+5G 协同），维护一张制式→参数基线表（见下）；
  3. 参数基线回灌既有逻辑：缺口聚类粒度/建议站点间距随覆盖半径变、单站 `capacity` 上限随制式变、塔桅与 BOM 随制式选（5G 用 AAU、4G 用 RRU+天线）。
- **进度（2026-08-13 已实现，A+B 一次做）**：
  - **Phase A 技术制式维度（低风险增量）**：新增 `models/tech.py`——`TechGeneration` 枚举（4G LTE / 5G NR(Sub-6) / 5G NR(mmWave) / 4G+5G协同）+ `TECH_BASELINE` 参数表（覆盖半径/建议站间距/单站容量参考/塔桅形态/设备项）+ `get_baseline()` / `default_band_for()`（制式→默认频段键，对齐 `BAND_CONFIGS`，缺省回退 4G+5G 协同）。`models/site.py` 加 `tech_generation` / `coverage_radius` / `capacity` 字段及 GeoJSON 往返（旧数据缺键回退默认）；`bill_of_materials()` 按制式追加 AAU/RRU+天线等设备项。`ui/design_dock.py` 加技术制式下拉 `_on_tech_changed`（预选默认频段+刷新覆盖半径/站间距/容量/塔桅信息）；生成站点透传 tech/capacity/coverage_radius。默认制式=4G+5G 协同，与现状零破坏。
  - **Phase B greenfield FTTH 生成（高风险新增模块）**：新增 `ftth/design_generator.py`（**纯 Python、不依赖 shapely**，离线可测）——射线法点面判定、`_synth_buildings` 楼栋网格合成、`_pipeline_nodes` 沿管线取样、OLT 落机房、FD 光分纤箱沿管线布放、光缆按 trunk/drop 合成。`generate_ftth_design(rooms, area_poly, pipelines, buildings, split_ratio, building_grid_m, fd_sample)` → 返回 `{ZNRO, FD, IMB, CABLE, stats}`；无机房/无区域抛 `ValueError` 守卫。`ui/design_dock.py` greenfield 才显示「生成 FTTH 设计（机房+管线）」按钮（`_on_generate_ftth_design` → `_render_ftth_design` 渲染 OLT/楼栋/光缆三内存图层，色值用 6 位 hex 跨版本安全），banner 文案更新为已实现描述；所有 greenfield 代码 `if build_mode=="greenfield"` 包裹，brownfield 路径字节级不变。
  - **验证**：四文件 `py_compile` 全绿；模型层（制式→频段映射、Site 往返、BOM 含 AAU/RRU、旧数据回退）离线自测全通过；生成器（点面判定、无管线/有管线、无机房异常守卫）全通过；dock 数据装配与生成器契约一致（集成自测通过）。
- **通信技术参数基线（示例，待校准）**：
  | 制式 | 典型频段 | 覆盖半径(宏站) | 建议站间距 | 单站容量参考 | 塔桅/设备形态 |
  |------|----------|----------------|------------|--------------|----------------|
  | 4G LTE | 1.8–2.1GHz | 1–3 km | 0.8–1.5 km | 中 | RRU + 天线 |
  | 5G NR(Sub-6) | 3.5GHz | 0.25–0.5 km | 0.2–0.4 km | 高 | AAU(有源天线) |
  | 5G NR(mmWave) | 26/28GHz | 0.1–0.2 km | 0.1–0.15 km | 极高 | 小微站/灯杆站 |
  | 4G+5G 协同 | 多频 | 取短板 | 取 5G 间距 | 叠加 | 多频天线/AAU |
- **工作量**：大（架构级，涉及 FTTH 生成器 + 技术参数基线 + 多处参数回灌）
- **风险**：高，易影响现有「现网补盲」演示稳定性；参数基线需行业参考值校准，否则建议站点过密/过疏。
