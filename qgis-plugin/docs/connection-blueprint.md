# 跨专业连接蓝图：FTTH 现网 与 基站/管线/机房 设计如何连起来

> 文档目的：回答一个核心困惑——「FTTH 是固定的现网数据，怎么和我设计的基站/管线/机房连起来？」
> 结论先说：**FTTH 不是孤立数据，连接机制已经内建在 9 步面板里**。FTTH 是「现状输入」，基站/管线/机房是「设计产物」，二者通过「统一 GIS 画布 + 机房/管线共享锚点 + 第 8 步跨数据集联动」三把钥匙串起来。

---

## 1. 一句话定位：谁是什么

| 对象 | 在系统里的角色 | 数据来源 | 代码位置 |
|------|----------------|----------|----------|
| FTTH 8 层 | **现状 / 已建固网**（摩洛哥 JAD-MAR 真实 Shape） | 加载 Shape 文件夹 | `self._ftth_layers`（8 个 QgsVectorLayer） |
| 基站（Site） | **无线侧设计产物**（新建/规划站点） | 拓扑引擎生成 / 手动添加 | `models/site.py` + `ui/station_dialog.py` |
| 机房（MachineRoom） | **共享锚点**（固网 OLT、无线 BBU 都落在这里） | 地图点选 / 手动添加 | `models/machine_room.py` + `ui/room_dialog.py` |
| 管线（Pipeline） | **共享锚点**（固网光缆、无线回传都敷设在管内） | 路由算法生成 | `models/pipeline.py` + `layers/pipeline_layer.py` |

**关键认知**：FTTH「固定」不是缺陷，而是它的定位——它是已经建好的真实网络，扮演「设计输入」：用来找覆盖盲区、建议补站。你要连的基站/管线/机房，是在同一张 GIS 画布上**叠加设计**出来的，不是去改 FTTH 本身。

---

## 2. 9 步面板里连接发生在哪里（代码实证）

`design_dock.py` 的 9 步就是一条「先载现状 → 再叠设计 → 最后联动」的流水线：

```
① 环境·底图  →  ② FTTH 现网(加载固定 Shape)  →  ③ 覆盖缺口识别
        ↓
④ 设计区域  →  ⑤ 基站参数  →  ⑥ 生成布局(基站)  →  ⑦ 管线·场景(机房+管线+热力图)
        ↓
⑧ 自检·联动  ←★★ 这一步就是「FTTH ↔ 基站/管线/机房」连接点 ★★
        ↓
⑨ 出图·交付
```

- 第 ② 步：`_load_ftth_layers()` 把 FTTH 8 层读进 `self._ftth_layers`。
- 第 ⑤–⑦ 步：你设计的 基站 落为图层「**基站设计**」，管线落为图层「**通信管线**」，机房以 RubberBand 标记。
- 第 ⑧ 步：`LinkageQueryTool`（点击地图）→ `_on_linkage_clicked(lon, lat)` 做半径查询，**同时高亮三类图层**。

## 3. 连接的三把钥匙（为什么能连）

### 钥匙一：统一 GIS 底座
所有专业叠在**同一 QGIS 画布、同一坐标系**。FTTH 的 IMB 楼栋、基站的 Site 点、管线的 Line 串、机房的 Room 点，都是地理要素，坐标天然可比。这是连接的前提，QGIS 插件天然具备。

### 钥匙二：共享锚点 = 机房 + 管线
- **机房**：FTTH 的 PM/OLT 和基站的 BBU 都物理落在机房里。系统里 `MachineRoom` 是独立模型，FTTH 和基站都「挂」到它。
- **管线**：FTTH 光缆（CDI 编号）和基站回传都敷设在管孔内。`Pipeline` 模型用 `start_site_id` / `end_site_id` 关联站点，天然串起「基站↔机房↔FTTH」。

> 连接的本质 = **共享锚点 + 同一 GIS**，不是把两段代码硬绑。改 FTTH 代码是错的，让 FTTH 和基站都引用「机房/管线」两个锚点才是对的。

### 钥匙三：第 ⑧ 步跨数据集联动（最核心）
`ui/design_dock.py` 第 2399 行的 `_on_linkage_clicked` 实现：

```python
targets = []
# 基站设计
for lyr in QgsProject.instance().mapLayersByName("基站设计"):
    targets.append((lyr, QColor(0,120,255), "基站"))
# 通信管线
for lyr in QgsProject.instance().mapLayersByName("通信管线"):
    targets.append((lyr, QColor(0,120,255), "管线"))
# FTTH 8 层
for name, lyr in (self._ftth_layers or {}).items():
    targets.append((lyr, QColor(239,68,68), "FTTH"))

# 以点击点为中心、radius_m 为半径，逐层查要素并 RubberBand 高亮
```

点一下地图某处 → 蓝圈标出附近的**基站**和**管线**，红圈标出附近的 **FTTH 楼栋/光交箱**——三个专业在「同一个点」被一起点亮，这就是肉眼可见的「连接」。

## 4. 数据层连接：上传时一起送后端

`design_engine/data_sync.py` 的 `upload_design(project_id, sites, ..., machine_rooms=...)` 把**基站(sites) + 机房(machine_rooms)** 打包推到 M03 拓扑引擎后端：

```python
design_data = {
    "projectId": project_id,
    "sites": site_list,            # 基站设计
    "machineRooms": rooms_data,    # 机房（共享锚点）
    "routeType": route_type,       # 管线路由类型
}
```

即：基站和机房作为**同一份设计成果**提交，后端据此生成拓扑（扇区覆盖、设备清单）。FTTH 现网作为「背景约束」在联动和设计审查时参与，但不作为「待生成」产物上传。

## 5. 你之前为什么觉得连不起来（病根）

1. 只走到第 ②–③ 步看 FTTH，没进入 ⑤–⑧ 步叠加基站/管线、也没点联动。
2. 想「删 FTTH 层造缺口」是错路——真实数据全覆盖，删层只会让功能无几何可判（已修：删层后联动/缺口不再崩溃，见 `coverage_gap._live_layers`）。
3. 联动需要「基站设计」「通信管线」图层**确实存在**才看得到蓝圈；若没生成这些层，点击只高亮 FTTH 红圈，看起来像「只有 FTTH」。

---

## 6. 正确演示「连起来」的操作流（照做即可）

1. 打开插件 → 第 ② 步「加载并符号化 FTTH 图层」（摩洛哥数据）。
2. 第 ⑤ 步设基站参数 → 第 ⑥ 步「一键生成基站布局」（生成「基站设计」层）。
3. 第 ⑦ 步在地图点选加机房、生成「通信管线」层。
4. 第 ⑧ 步「自检·联动」→ 在地图某处**左键点击一个 FTTH 楼栋附近的点**。
5. 观察：红圈（FTTH 楼栋/光交箱）+ 蓝圈（附近基站 + 经过的管线）同时亮起 → **这就是连接效果**。

> 若想看到「缺口红圈」，需一份**覆盖不全**的 FTTH 样例（挪掉部分 ZNRO/ZPM 面或偏移 IMB 点），真实摩洛哥数据覆盖完整、gap=0。

## 7. 当前连接的边界与下一步（S4/S5 扩展方向）

| 现状 | 说明 | 扩展方向 |
|------|------|----------|
| 连接靠空间邻近 | 联动是基于「点击点半径内三类图层要素」高亮，无强外键 | S4 设计转施工：把 FTTH 光缆路由、基站回传都落到「管线」CAD，用管线 ID 做硬关联 |
| 机房是弱锚点 | 基站/FTTH 都引用机房坐标，但 FTTH 层内未存 room_id 外键 | 在 FTTH 数据模型补 `served_room_id`，使固网↔机房可追溯 |
| 上传只含基站+机房 | FTTH 现网不上传，仅作背景 | S5 施工监管可把 FTTH 现状作为「已建基线」与新建对比 |

## 8. 建设顺序安排（机房先行原则）

真实通信工程建设中，**机房是第一性基础设施**——提供供电、防雷、设备安装空间，也是固网 OLT 与无线 BBU 的共同落点和回传终结点。没有机房，FTTH 与基站都无从谈起。用户直觉正确：目标区域应先建机房，再想其他的。

### 8.1 两种建设范式

| 范式 | 适用场景 | FTTH 角色 | 建设顺序 |
|------|----------|-----------|----------|
| 现网补盲 (brownfield) | 区域已有 FTTH（如摩洛哥数据） | 固定基线（已建） | 加载 FTTH → 找缺口 → 缺口处补机房/管线/基站 |
| 新区新建 (greenfield) | 目标区域为空地/无覆盖 | 设计产物（待建） | 定区域 → 建机房 → 铺管线 → FTTH 设计挂接 → 基站挂接 |

插件当前 9 步 = **现网补盲范式**：第②步先加载 FTTH 固定现网，第③步找缺口，第⑤–⑦步在缺口处补基站/机房/管线。这是「优化已建网络」的逻辑，顺序正确。

### 8.2 机房先行原则在插件里的落点

第⑦步「管线·场景」（`_build_step7`，design_dock.py:775）已实现**机房先行**：先「在地图上点击添加机房」，再「生成基站到机房的管线并核算工程量」。即机房是锚点，管线从机房向外辐射，FTTH/基站的设计都挂在这个锚点上——只是因棕地范式，机房用来「补缺口」而非「打地基」，所以排在流程后半段。

### 8.3 FTTH 如何与「之前的建设结果」结合

- **棕地（现网）**：之前建的 FTTH 就是「之前的建设结果」（基线）；用第③步覆盖缺口识别找盲区，在盲区补建机房/管线/基站——以现网为约束做增量设计。
- **绿地（新建）**：先建的机房就是「之前的建设结果」；FTTH 设计（OLT 落机房、光缆走管线）必须引用该机房，基站同理。结合点 = 机房锚点 + 管线共享通道。
- **可视化结合**：第⑧步联动点击，红圈(FTTH) + 蓝圈(基站/管线) 同亮，即「建设结果组合」的肉眼呈现。

### 8.4 给插件的改进建议（让「机房先行」可选）

1. **加「建设模式」开关**：现网补盲 / 新区新建。新建模式下 FTTH 不再是「加载固定 Shape」，而是变成可设计的输出（OLT/光缆由用户在机房锚点上布放）。
2. **数据层硬关联**：给 FTTH 数据模型补 `served_room_id`（每个 PM/BPE 归属哪个机房），使固网 ↔ 机房可追溯，而非仅空间邻近。
3. **顺序提示 UI**：第④步「设计区域」后显式提示「请先布置机房（第⑦步上半），再生成管线与基站」，把机房先行做成引导。

## 9. 术语对照（答辩用）

- **FTTH**：光纤到户固网（现状网络）。
- **Site/基站**：无线侧新建/规划站点（宏站/微站/室内站）。
- **MachineRoom/机房**：汇聚/接入/核心机房，固网 OLT 与无线 BBU 的共享落点。
- **Pipeline/管线**：管道/直埋/架空管线，承载固网光缆与无线回传。
- **联动(Linkage)**：点击地图 → 半径内跨数据集高亮，是各专业「连起来」的肉眼呈现。
